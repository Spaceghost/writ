Bend running as a Genode component

Change add-genode-bend-component. How a Bend-built monitor becomes a Genode component, how its effects reach Genode sessions, and how it serves requests when Genode speaks C++ RPC and Bend speaks a C event loop. Proposed; nothing built.

The gap this fills

The Genode host change already exists and is large: fourteen requirements about confinement, sealing, revocation, quotas, and restarts. Its task 1.2 says "port and verify the required Bend runtime/ABI surface" and task 1.3 says "implement native channel registration." Neither says how. Genode's RPC interface is a C++ framework API; Bend's generated program is one C file with its own event loop. Until the monitor can exist as a component and answer a request, none of the fourteen requirements can be exercised.

The hook: Bend's custom effects

An effect in Bend is a def whose body is two imports, a .c twin and a .js twin. The compiler splices the .c file into the generated program after the runtime, so every runtime symbol is in scope. That is the whole mechanism Base uses for files, sockets, and timers, and Writ can use it for Genode.

# authored in Bend, inside Writ
def Genode.log(text: String) -> IO(Unit):
  import "./genode_log.c"
  import "./genode_log.js"

def Genode.accept() -> IO(Request):      # parks until a session delivers a request
  import "./genode_accept.c"
  import "./genode_accept.js"
/* the C twin: a few lines that call one shim */
Term genode_log_run(Env e, Term* f, IoWork* w) {
  uint64_t n = 0; char* text = io_cstr(e, f[0], &n);
  writ_shim_log(text, n);                 /* extern "C" over Genode's LOG session */
  free(text);
  return term_pak(CID(Unit), 0);
}

The shim is the only authored C++: one translation unit that owns the Genode environment and session objects and exports extern "C" functions. It contains no policy. AGENTS.md allows authored binding code only with an explicit source and trust inventory, so the shim ships with one.

Data-centric above the kernel: a Writ channel is a request bucket and a result bucket the monitor owns for one descriptor, plus a signal. Clients append request records and read result records; nothing above Genode's transport is a procedure call. One record at a time, because the backplane requires one authoritative state at commit. Genode.take parks on the runtime's wait mechanism (a pipe on base-linux, a signal receiver bridged to the libc wakeup on base-hw) until the shim has a record.

Runtime rows on Genode's libc

Genode's libc is FreeBSD-derived. For each row of the runtime inventory the port must record supplied, substituted, or missing, by running it, on both base platforms. Expectations to test, not assume:

The fault row is the one to settle first. If libc signal delivery cannot reach the runtime's handler, the profile's halting substitute applies: the component dies, the parent records it, nothing resumes. That is acceptable. A handler that returns is not.

GB-002Every runtime row recorded per base platform, established by execution. A header is not evidence.
GB-003Faults terminate the component with the fault recorded by the parent; restart gets a new generation.
GB-004Corpus parity inside the component on each base before any session is served.
GB-005Effects are Bend defs with C twins. Policy in C++ fails review.
GB-006The shim is the only authored C++, inventoried, bounded in queue depth and request size.
GB-007Requests carry the parent route's identity; a subject claimed in the body never replaces it.
GB-008One request at a time under fuel; an unresponsive client cannot block others.
GB-009base-linux and base-hw recorded separately; device paths recorded as CPU.

Milestones

  1. Pin Genode 26.08 and a base-linux run script. Compile the generated C of the hello program as a component. See its line in the Genode log.
  2. Execute every runtime row on base-linux. Decide the fault substitute from the result.
  3. Corpus and examples as components on base-linux. Line-for-line match with the Linux single-lane record.
  4. Log, now, sleep effects over the shim. Then accept and answer. Serve one report-to-summary request and one with a substituted subject, denied by Bend.
  5. Bound request size and queue depth. Prove liveness against a client that never reads.
  6. Repeat corpus and the served request on x86_64 base-hw under QEMU. Separate record.

Not in scope

  • Worker topology, input dataspaces, result collector, sealing, revocation, quota behavior. Those are the Genode host's tasks 1.4 through 2.4 and stay unchecked.
  • GPU. Genode's GPU session is not a Bend compute backend. Device paths run on the CPU and are recorded as such.
  • Any claim that base-linux evidence transfers to base-hw, or vice versa.

Where a subagent starts

This lane needs a Genode build environment, which is the slowest part. A subagent should begin by pinning Genode 26.08 at commit d18ee9e, building a base-linux run script with a trivial component, and only then substituting the generated C. The second thing it should do is execute the fault row, because the answer shapes the rest of the port. It should read docs/GENODE.md, docs/BEND-RUNTIME.md, and bend guide effects before writing anything.

It should coordinate with lane B: Genode.accept constructs the binding records that lane B's model defines, and must replay lane B's vectors.
