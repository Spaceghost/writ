Shim review 3 of 9: making and releasing a reservation

A qualifying mmap becomes a reservation: address space that is set aside but has no memory behind it yet. Genode terms: a dataspace is a piece of memory (or address space) that can be referenced by capability and attached into an address space. A Region_map is an address-space layout: a set of dataspaces attached at offsets. A region map can itself be exported as a dataspace (a "managed dataspace") and attached into another region map. An Rm_connection is a session to the RM service that creates such region maps. So _reserve asks the RM session for an empty region map of the requested size, attaches it into the component's own address space (Env::rm()), and records it in a fixed table of 32 slots. Nothing is populated, so no RAM is charged here. Read the table struct first (378-435), then _reserve and _release.

Claim 3

A qualifying request above MAX_RESERVATION (1 TiB), or with all 32 slots used, fails with ENOMEM before anything is created. The comment records that the 1 TiB bound also caps the runtime's corpus_grow.

916	static void *_reserve(void *hint, size_t len)
917	{
918	    /*
919	     * Bound len before any rounding: a len above SIZE_MAX - 4095 would
920	     * page-round to 0 and create an empty region map. 1 TiB is far above
921	     * what any quota can populate (and base-linux's region map holds at
922	     * most 4096 pieces, 8 GiB of 2 MiB chunks), so a larger request fails
923	     * with ENOMEM exactly as an exhausted address space would. The Bend
924	     * runtime's corpus_grow treats that as "cannot grow". The bound
925	     * therefore also caps corpus_grow, which doubles the term heap in
926	     * place by mapping a span as large as the current one at its end
927	     * (requests up to 4 TiB): growth stops after the 1 TiB request, at a
928	     * 2 TiB corpus, and the runtime then posts ERR_HEAP ("out of memory").
929	     */
930	    if (len > MAX_RESERVATION) { errno = ENOMEM; return MAP_FAILED; }
931	
932	    Reservation *r = nullptr;
933	    for (Reservation &cand : _res)
934	        if (!cand.used) { r = &cand; break; }
935	    if (!r) { errno = ENOMEM; return MAP_FAILED; }

What I see. Both checks run before any allocation. The 1 TiB bound also prevents a length that would round to zero, and it stops corpus_grow at a 2 TiB corpus. The 32 slots cap lanes at about 30 (INVENTORY.md:379-383). These are fixed capacity bounds that read no Writ fact; they affect how far the runtime can grow, not who may do what.

Recommendation: Confirmed, the bounds sit before any allocation and are constants.
