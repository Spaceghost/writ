# Design only: exploratory zero-capability Win32k contrast

In [run 42322440747](run-42322440747/README.md), four no-data LPAC initializations with Win32k system calls disabled returned USER32 status 1114 and OLE32 status 1359, whether the token had no capability or registryRead. A small follow-up could observe whether those numeric results differ when only the requested Win32k mitigation setting changes. This is a proposal, not an implementation, an authorized run, or evidence of a cause.

## Fixed comparison

Use one fresh, disposable, no-data package and four separate retained child lifetimes in A/C/C/A order, bracketed by the existing ordinary positive controls. Both arms have **zero capabilities**, the same fixed no-data child image and private executable, reduced launch token and LPAC package, process/job/UI restrictions, explicit single inherited report-pipe handle, four package WFP blocks, fixed input environment and output-only protocol. No Writ session, public or protected canary, caller-supplied data, arbitrary image/handle/path, byte worker, policy pipe or policy engine is allowed. Windows loader and provider code may itself consult OS state; do not collect that state or its contents.

For A request `PROCESS_CREATION_MITIGATION_POLICY_WIN32K_SYSTEM_CALL_DISABLE_ALWAYS_ON`; for C request `PROCESS_CREATION_MITIGATION_POLICY_WIN32K_SYSTEM_CALL_DISABLE_ALWAYS_OFF`. Microsoft documents both creation-policy values in [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). Before resume, on the retained child's creation-returned process handle, call [GetProcessMitigationPolicy](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessmitigationpolicy) for `ProcessSystemCallDisablePolicy`; require `DisallowWin32kSystemCalls` to be 1 for A and 0 for C. The [documented structure](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-process_mitigation_system_call_disable_policy) describes that field, but a zero readback is not proof that GUI calls or initialization will succeed. Reject failed/unsupported query, unexpected output, or inability to establish those exact states; do not relax another control to make C launch. Compare other returned policy bits across all cases and report unknown or differing bits as incomplete, without assigning undocumented meaning to reserved bits. Record both intended creation inputs and actual readbacks. C has no established GUI or ambient-resource confinement: it must not add clipboard, screen/input, window-enumeration, COM-activation or socket/traffic probes. Keep the existing strict byte-worker launch and acceptance gate unchanged.

All cases must independently verify actual LPAC package/user, low integrity, non-elevation, zero `TokenCapabilities`, selected groups, restricted SIDs, privileges and authentication LUID; compare those selected canonical facts to the first case, including the zero-capability check. Record scope and counts while keeping raw token fields private. Verify the same configured child job limits and UI restrictions, process-child policy, image digest, package SID and all four owned WFP filter identities, layers, action and package conditions before and after each case; record configured limits separately from volatile counters. Compare the constructed environment input privately before and after each launch, while explicitly retaining that the child's full environment is not independently read. The exact shared owned resources and their cleanup semantics follow the [registryRead implementation record](registry-ab-implementation.md); if any required control is unavailable, different or unknown, stop with an incomplete comparison.

## Bound observation and failure

For each fixed self-created child, keep its original process and thread handles, PID and creation time; snapshot its suspended pre-resume handles with PSS, require bounded before/captured/walked/after agreement and exactly the expected synthetic report-pipe value, and positively compare the duplicated known pipe to the retained original. Close the duplicate, PSS marker and snapshot with checked outcomes, close the parent's writer, and resume the original thread exactly once only if its previous suspend count is 1. Require that same child to exit within the deadline, exactly one valid fixed-size report, EOF without trailing data, cold-load preconditions and checked cleanup. The snapshot applies only before resume: it says nothing about handles or possible paths created during initialization. Record raw bounded Winsock/USER32/OLE32 codes and module timing even if a later acceptance gate fails, without interpreting them as a denial or successful confinement.

Use an observer-only bounded job, child job and an external wall deadline on a fresh hosted Windows VM. Read back the observer job limits and membership, and verify the child is outside that observer job and inside its own unchanged restricted job; unsupported nested-job or breakaway behavior is incomplete. If termination, child exit, snapshot release, any handle, WFP/session/profile/image cleanup or setup-output ownership cannot be verified, mark the case and sequence incomplete, stop before another case, and retain shared controls when child exit is unknown; disposable-VM destruction is fallback, not verified in-guest cleanup. Normal shared cleanup must close the owned dynamic WFP session and use a separately owned observer engine to verify all four retained filter IDs are absent; an unsuccessful close, readback or observer-engine cleanup is incomplete. Preserve source and binary hashes, child PE import inspection, exact runner/ref, raw logs and artifact hashes, including failures. The workflow must select only this design's dedicated job on its exact experimental branch; temporary dispatch scaffolding stays off master.

Before any separately reviewed implementation or run, add meaningful synthetic tests for both requested/read-back mitigation states, unexpected or mismatched other bits, nonzero capabilities, A/C/C/A stop conditions, identity/pipe/report and EOF failures, timeout and cleanup uncertainty. Synthetic classifiers do not demonstrate Windows API behavior, and native adapter failure-path injection remains a gap unless actually implemented and run.

Neighboring cases differ in one verified configured mitigation field only under the recorded assumptions. Sequential cases share a package and can affect package caches, registry or transient OS/provider state; ordering and drift, unobserved environment differences, snapshot perturbation and incomplete OS state remain possible confounders. An A/C pattern can guide another hypothesis but cannot establish a causal mechanism, full process equivalence, byte-worker confinement or host qualification; it does not change the strict worker failure. If even one required field is unknown, the comparison is incomplete.
