# Design alternatives: same-worker handoff and reachable-resource control

The existing strict public-canary worker receives its mount and fixture metadata in its command at creation, then writes reports through one inherited pipe and synchronizes through two events. The [feasibility review](same-worker-pre-admission-feasibility.md) and [transition obligations](pre-admission-handoff-obligations.md) identify a missing broker-to-worker handoff and an unresolved reachable-state/race proof. This is a source-backed design comparison, not an implementation, approval to add an authority channel, or evidence of confinement.

## Handoff alternatives

| Alternative | What Windows supplies | Main unresolved costs |
| --- | --- | --- |
| Broker-created, one-way pipe read endpoint inherited at launch | [CreatePipe](https://learn.microsoft.com/en-us/windows/win32/ipc/anonymous-pipe-operations) returns distinct read and write handles; [the explicit handle-list attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) selects inheritable handles at creation | Adds a fourth inherited object and requires changing `writ_worker_create`'s current limit of three. Handle possession selects an object, not a Writ identity. Anonymous pipe writes are synchronous and can block; robust bounded cancellation/cleanup and peer/object ownership are not yet demonstrated. |
| Broker creates a pipe and duplicates a read endpoint into the retained worker after launch | [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) can create a handle in the target process given `PROCESS_DUP_HANDLE` access | Requires a safe way for the correct lifetime to learn the new handle, strong limits on who can duplicate into it, race-safe identity/object binding and cleanup of failure outputs. A handle number is not authentication. Adds target-process authority and complexity. |
| Named-pipe connection after launch | [CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew) supports overlapped I/O, first-instance enforcement and rejecting remote clients | Adds namespace, connection and impersonation/peer-authentication surfaces; a random name, same SID or PID alone is not authority. A restrictive descriptor and exact access masks need review; Microsoft notes [generic write can include pipe-instance creation](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights). |
| Keep today's public canary metadata in initial arguments | Requires no later data-bearing handoff | It is not the stronger proposed no-data-path preflight. It might be reviewed as a separate public-fixture experiment, with its narrower scope explicit; accepting that changed boundary is a security-design choice. |

The best **candidate for a narrowly scoped feasibility design** is the inherited read-only endpoint: the broker creates one private one-way pipe before worker creation, retains its write end, and passes only the child read end in an explicit four-object launch list alongside the existing three objects. `CreatePipe` is implemented using a named pipe internally; do not infer that "anonymous" proves namespace secrecy or denies every other opener. Specify and check object security and which parties can acquire or duplicate either end. This option avoids a post-launch named client connection and avoids granting the worker a pipe write endpoint, but still adds a reachable input channel and does **not** solve ambient-resource confinement or authority binding. It is not approved or demonstrated.

## Candidate contract to review

1. Start one exact held strict probe image suspended with fixed command syntax naming only its inherited test handles and fixed preflight mode, without mount path, fixture digest/size, public outside path or ports. No Writ policy pipe, protected bytes, fixture handle or data-bearing mount handle is inherited. Retain creation-returned process/thread handles, creation time, PID and image digest; require the original token, job/UI/child, Win32k, WFP and no-weak-fallback settings. Independently verify actual controls under the chosen supported APIs; do not assume the handle-list input proves the worker's complete reachable resources. Require initial `ResumeThread` previous count 1 if this new contract relies on that transition.
2. The fixed worker executes only bounded no-data initializers and sends one versioned, length-checked, phase-specific report over its existing one-way report route, then waits for the handoff. The broker treats all returned bytes and numeric statuses as untrusted observations. They neither create actor authority nor prove a forbidden effect denied; a generic initialization failure remains incomplete. The existing auto-reset event is synchronization only, not peer identity or a grant. Specify a deadline and classify malformed, duplicate, extra, truncated, stale and missing reports as failure.
3. Before handoff, retain the actual worker lifetime and revalidate real OS controls, session/monitor generation, worker-to-actor binding and Bend authorization requirements. The preflight must remain unadmitted and have no protected input route; since the present dispatcher and actor checks rely on Bend, require explicit negative pre-admission `STAT`/`OPEN` tests and verify there is no alternate route. PSS can supplement retained-object checks but its instantaneous table is not proof of continued absence, quiescence or an independently verified environment.
4. After the reviewed no-data preflight completes and while the actor is still unadmitted, send one bounded, versioned, one-shot public-fixture parameter record on the private inbound channel: fixed-format mount location, fixed-size digest and bounded length, the owned public outside-test path and four broker-created public receiver ports. These are test inputs, never caller-supplied authority, actor identity or a policy decision. Reject unknown fields, invalid lengths, duplicate records, wrong phase, timeout, trailing bytes and unexpected peers. The exact encoding, maximum sizes, object rights, first-writer rule and end-of-stream handling remain to be designed and reviewed; do not transmit protected bytes through this control channel.
5. Require worker and broker to close their respective handoff endpoints after the single record and before actual actor admission, check completion/EOF as appropriate and account for all possible duplicate endpoints. The original report pipe and two events still survive for the real worker's three phases and must be independently mediated under the declared policy. A PSS observation or a worker's closure report alone cannot establish complete, race-free absence of duplicates or other output routes. If that property cannot be established with supported enforcement, do not admit protected input under the stronger claim.
6. After the handoff is retired or explicitly mediated, serialize the final Bend admission and any state transition with revoke/restart/commit so a stale handoff, monitor incarnation, capability, epoch, scope, inherited restriction or budget cannot gain authority. Define the exact lock/transaction ownership and failure handling without blocking a protected commit indefinitely on a synchronous pipe write. If revocation wins before delivery, no protected input is released; if it follows delivery, prevent later use and stale uncommitted release without claiming to erase already observed bytes. The fixed probe's existing effect tests, positive controls, revocation and strict fail/incomplete gate still run in the same worker; preflight is not a replacement.

[Anonymous pipes do not support overlapped I/O](https://learn.microsoft.com/en-us/windows/win32/ipc/anonymous-pipe-operations), and a synchronous write may wait while a nonreading worker fills the pipe. The repository's `policy_pipe.c` uses a separate writer thread, `CancelSynchronousIo`, job termination and an emergency process termination if a writer cannot retire; that design is a precedent to study, not proof this new channel is safe. Any chosen deadline must account for cancellation races, writer buffer lifetime, exact close/EOF ordering, broker/worker crash and bounded cleanup; synthetic fault injection and an isolated Windows test are prerequisites. An overlapped named-pipe design may solve part of the I/O deadline problem but brings the namespace and access-control concerns above.

records the proposed effects, trusted-input assumptions and native evidence
gaps. It is a design sketch, not an implemented or qualified host path.

## Reachable-resource control: evidence and nonclaims

The smallest reviewable authority deliverable is a per-channel matrix listing (a) construction and owner, (b) creation/transition/commit lifetime, (c) exact access rights and allowed peers, (d) enforcement for reads and writes, (e) how independently authenticated identity and current Bend scope are bound, (f) tested negative and ordinary positive controls, and (g) verified retirement or explicit unknown. It must include both pipe directions, both events, process/token handles, mount and public outside path, receiver sockets, profile/registry/cache state, console/desktop, mappings, logs/errors/timing and any resources opened by initialization. Object or token readback is evidence of a specific fact; the security argument must cover *all admitted routes and continuous enforcement*, not claim that a finite snapshot proves absence of all possible OS access.

The actual worker can create threads and open resources after a snapshot. The no-data initialization phase can itself perturb process and shared OS state. No documented method identified here both freezes all relevant threads/resources and binds a complete handle/environment/OS-state view through admission. A fixed self-created probe's earlier PSS observation cannot fill that gap. Depending on the selected policy, reviewed persistent OS isolation, mediated channels and current identity checks may support a bounded claim without literal enumeration of every future handle, but the needed evidence is not yet established. If a path or current authority cannot be bounded and enforced, deny protected dispatch and preserve the strict result as incomplete.

## Decisions and evidence still needed

Source research and a Bend-authored synthetic model can proceed now. Treating a newly reachable inbound channel, relaxed preflight boundary, broader capability/Win32k settings or changed acceptance rule as part of the protected design requires an explicit, independently reviewed security-design decision that preserves the stated laws; seek user input only if genuinely needed. First provide a concrete endpoint-rights/peer-binding proposal, explicit effect inventory, threat model for a malicious worker, authenticated generation and race-safe commit/revoke ordering, plus synthetic failure/replay cases from the [matrix](pre-admission-handoff-obligations.md). If the proposed argument depends on an unavailable readback, a potentially blocking I/O cancellation or unverified cleanup, state that as incomplete rather than assuming it. Source/spec behavior and native probes remain unimplemented until separate review; no separate diagnostic child may earn the real worker's confinement credit.
