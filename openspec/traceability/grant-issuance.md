# Grant issuance traceability

Proposed change: [add-authenticated-grant-issuance](../changes/add-authenticated-grant-issuance/specs/grant-issuance/spec.md).
This change is proposed. Nothing here marks a host adapter, a facade entry
point or an acceptance scenario as implemented: the issuance model exists in
Bend only, it is not wired to any host, and the DataOS facade has no issuance
entry. Every `from: Principal`, directory, placement, live stamp, `now` and
token in the tests is a synthetic fixture standing in for a trusted host
input; [docs/GRANT-ISSUANCE.md](../../docs/GRANT-ISSUANCE.md) lists each one and
who must supply it.

Implementation: [Issuance.bend](../../Issuance.bend) (public entry points
`empty`, `submit_source`, `submit_write`, `register`, `revoke`, `derive`,
`current`, `valid`, `reads`, `writes`, `registry`). Use-time checks, unchanged:
[Transfer.bend](../../Transfer.bend) (`admit`) and
[Frontend.bend](../../Frontend.bend) (`mount`, `open`, `checked_plan`).
Executable cases: [IssuanceTests.bend](../../IssuanceTests.bend) and
[FacadeTests.bend](../../FacadeTests.bend), run by `bend Tests.bend`, with the
recorded run in [verification/grant-issuance.txt](../../verification/grant-issuance.txt).
Laws: [LAWS.bend](../../LAWS.bend), proved in [PROOF.bend](../../PROOF.bend)
under ordinary `bend PROOF.bend` (not kernel verified).

A named test below is an existing `PASS` label, quoted exactly. Tests whose
names start with "scenario" are the whole-lifecycle checks of section
`scenarios`: each starts from `I.empty(...)` and reaches every state through
the public entry points (the epoch advance's monitor install is the one
marked exception). "Reviewed-only gap" means the requirement, or the named
part of it, has no execution here; the gap is stated in the requirement's own
words.

## Model details

Approvals are single use: a registration consumes every approval it cites,
and `(issuer, serial)` pairs stay in `seen` through revocation, so a replayed
or resubmitted approval is denied `Replay`. A derived grant never changes its
subject or scope and cites no approvals; a different subject needs a fresh
grant through full admission. Stored identities are the authenticated
principal the transition was called with, never a record field. The
projections are subject scoped: a list built for one principal holds only that
principal's current grants. Because a non-current grant leaves every
projection at once, a source revocation also denies at `Write` under
`Transfer.admit`'s check order.

One registration gate is not reachable by a whole lifecycle through the public
entry points: `DestinationIsPlans` in `register_gates`, because
`submit_write` already requires the approved destination to be the scope
plan's. It is exercised against a monitor-installed state by:
"GI-003 stored write approval for destination 20v9 under a plan naming 20v8 is revalidated and denied ScopeMismatch".

Not exercised anywhere in this change: transport authentication, signature
verification for approvals carried off-host, durable storage and recovery,
concurrent hosts, and any native host (Genode, Unikraft, Linux, Windows,
rclone).
