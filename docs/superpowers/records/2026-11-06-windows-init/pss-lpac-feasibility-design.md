# Proposed PSS observation of a fixed no-data LPAC child

Status: reviewed design with a first source implementation under review. No LPAC PSS observer has been built or run on Windows. The actual byte-worker launcher, profile, data path, strict native gate and preserved failed outcomes remain unchanged.

In [run 42316163834](run-42316163834/README.md), PSS captured an ordinary suspended synthetic child's handle table with counts 2/2/2/2 and matched two synthetic objects; that does not establish PSS availability or the same handle set under LPAC. Separately, [run 42313767360](run-42313767360/README.md) observed initializer errors in a no-data LPAC; it did not inspect the full handle table. A fixed LPAC PSS observation could test whether the snapshot technique works for one isolated LPAC creation. It would not determine why an initializer fails or establish the real byte worker's confinement.

## Fixed test boundary

Use a fresh disposable Windows hosted runner with no Writ mount, session, policy pipe, canary bytes, public input fixture or protected worker. A dedicated observer takes no caller-selected process ID, executable, command, handle, data or destination. It starts only its own fixed no-data child image, which is held suspended and never resumed, and creates only its own synthetic pipe and events. The only child inheritance inputs are a known pipe endpoint and event in an explicit handle list; a second inheritable event is deliberately excluded. The excluded event's absence can demonstrate only absence of that **numeric value** in this snapshot, not absence of the underlying object under another handle. The same-launch negative check is not a separately executed negative scenario.

Construct and inspect one LPAC using the unchanged byte-worker canary launch helper `writ_worker_create(..., lpac=TRUE)` and a fixed synthetic child, provided that all required ownership and failure behavior can be kept isolated. Its existing launch path creates a fresh package, uses reduced primary-token construction, zero capability SIDs, LPAC opt-out, one-process job with kill-on-close and UI limits, child-process restriction, disabled Win32k system calls, explicit handles, and four owned package-scoped WFP blocks. The existing helper performs its own native token/AccessCheck, job, child/Win32k and filter readbacks. Preserve those checks; do not add any token capability, change mitigation or remove WFP filters while the child exists merely to make the probe pass. Prefix all launcher stdout as no-data PSS diagnostic output, as the earlier standalone diagnostic does, so its generic `NATIVE_PASS` line cannot be mistaken for the real byte worker. Record actual return values, checked fields, process PID and creation time, source and both binary hashes. `AuthenticationId` is captured by the existing launcher; do not assert it was independently compared with an expected logon unless the new diagnostic explicitly does so. Do not claim that complete groups/privileges, exact original worker identity or environment equivalence were established.

The observer must use the process handle and thread handle returned by the self-created LPAC launch and never accept or reopen an arbitrary PID. Verify child liveness, PID and creation time against that retained process handle before and after the snapshot. Verify the child is outside the separate observer-budget job and inside its LPAC job, and verify intended child-job configuration with the existing launcher readbacks. Hold the original synthetic parent handles until comparison and retirement are complete. The child has its own native process lifetime and is not mapped to a Writ actor; matching token or package facts are not portable credentials. The exact access rights of the creation-returned process handle remain unqueried; failed PSS access is incomplete, never a reason to elevate privileges or inspect a different process.

## PSS observation and controls

On the retained, still-suspended child request only `PSS_CAPTURE_HANDLES`. No PSS memory, clone, names, environment, trace or thread-context capture is in scope. Query the snapshot handle count, cap it at 256, walk at most 256 fixed-size entries plus a terminal check, require `ERROR_NO_MORE_ITEMS`, exact agreement of captured and walked counts, no invalid or duplicate values, and stable `GetProcessHandleCount` before/after. Any API failure, terminal/count discrepancy, excess count, deadline, missing expected value or excluded numeric value present is incomplete. If Windows supplies any additional table entry, retain only bounded counts and classify the exact-set observation as incomplete until that entry is reviewed; do not silently allowlist it. A point-in-time handle table and agreeing counts still do not prove inheritance provenance or future state.

The two known values must occur. While the child remains suspended and the originals are held, use only the retained child's process handle to duplicate those two fixed synthetic handles into the observer and compare each with its matching original using the documented `CompareObjectHandles` API; close the duplicates and verify closure. Missing API/module, insufficient `PROCESS_DUP_HANDLE` access, mismatch or any duplicate/close failure is incomplete. Do not duplicate arbitrary discovered handles, use `DUPLICATE_CLOSE_SOURCE`, request PEB memory, apply debugging privileges, or transfer any handle to Writ. Any additional rights used by the observer are local to this no-data child and do not change its token or give it new handles.

Portable classifier tests should cover count overflow, duplicates, missing expected values, an unexpected excluded value, extra entries, failed/partial walk and failed cleanup. The authored portable classifier tests missing/failed stage bits, timeout and cleanup ordering; they do not inject Windows API, timeout or cleanup failures through the native adapter. Adapter-level fault injection for PSS denial, marker/query failures, incomplete walk, identity drift, object-comparison failure, timeout and each cleanup failure remains a gap; no injected result may become a real native pass. Those synthetic cases test classification and teardown decisions, not Windows behavior. Preserve the earlier ordinary-child observation as a separate control; a later run may repeat an ordinary synthetic case on the same VM, but must report its own process, source, setup and cleanup instead of treating it as the LPAC identity.

## Cleanup and deadline

`writ_worker_create` can internally clean up and erase ownership state on setup failure. A setup failure therefore yields incomplete with cleanup unverified; do not infer resource retirement from the cleared structure. Destroying the disposable VM is fallback containment, not a verified scoped cleanup. Do not modify the shared worker just to manufacture cleanup evidence.

After a successful launch, require separate checked cleanup: free the walk marker and locally held snapshot; close the two comparison duplicates; terminate the suspended child and wait for its process handle; retain the job and WFP ownership until the child has exited; close its dynamic WFP session and confirm each of the four previously recorded owned filter IDs is absent through a separately opened readback engine; close and check all owned process, thread, job, image and fixture handles; delete only the created private image/directory and AppContainer profile. Reuse or factor the existing no-data diagnostic's checked-cleanup logic only after source review, and retain raw error statuses for each failure. Failed closure, missing filter IDs, readback failure or inability to delete a resource invalidates completion. Do not touch unrelated filters or profiles.

Before creating the child, place the observer in a separate observer-only job with an explicit per-process memory cap (128 MiB), user-mode CPU budget (15 seconds), one-process limit and `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`, and verify its configured limits and observer membership. Microsoft documents that [nested jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs) are formed only when neither job sets UI limits; the unchanged LPAC job does set them. The observer budget therefore allows its fixed child to leave that job. Verify the child is outside the observer job and inside its unchanged UI-restricted LPAC job; do not relax the child job. This creation-time job-list/breakaway interaction remains untested, and an inherited outer runner job can still impose constraints or prevent creation. If the jobs or membership cannot be configured and read back, stop incomplete. Do not claim exact byte-worker profile equivalence. Observer limits do not bound all PSS kernel-internal allocation.

The LPAC job's kill-on-close limits abrupt-observer orphaning when its last job handle closes; do not claim that this proves the child actually retired after a crash without an independent observation. PSS calls have no established internal allocation or wall-time bound in the researched documentation. Run the fixed observer under an external bounded supervisor that captures stdout/stderr, waits at most 30 seconds, requests termination on timeout, waits at most five more seconds and records cleanup as unverified; use an overall disposable-VM deadline as a fallback. Snapshot resources, protected resources and process contents are never written to artifacts. A timeout, observer crash, failed teardown or cancelled artifact upload is incomplete, not success.

## Separate future workflow and interpretation

Only after independent source and workflow review, place any future execution behind a distinct temporary exact-ref dispatch job, for example `lane/windows-pss-lpac`, on a fresh hosted Windows runner. The branch-specific guards must select this job alone, skip the older initialization and ordinary-PSS jobs and unrelated policy jobs, and leave the strict native workflow untouched. Build and hash all compiled sources, build configuration and binaries; run named synthetic tests with a no-tests error and retain their results, runner details, bounded PSS output, raw statuses and supervisor outcome. Do not commit generated binaries. Keep temporary workflow guards out of any eventual master integration. No run is authorized by this document.

The strongest possible result here is a single point-in-time observation of a **different no-data LPAC process** with the checked control facts, handle values and owned-resource cleanup recorded. It does not prove environment equivalence: the supplied environment is trusted launch input, and no supported independent pre-resume reader for the complete remote environment has been established. It also does not prove that this child equals the byte worker, that no information leaves via other paths, or that Windows host confinement is qualified. Any comparison depending on an unverified required fact remains inconclusive.

## Source implementation status

A first implementation uses the unchanged canary launcher and a temporary
exact-ref `lane/windows-pss-lpac` job. It is unbuilt and unrun on Windows.
The observer-only budget uses silent breakaway and checks that the suspended
child is outside that budget job and inside its LPAC job; creation-time job
semantics and any outer hosted-runner job are unverified. If child exit cannot
be observed, the implementation does not explicitly remove WFP or profile
resources and reports cleanup unverified; disposal of the runner remains
fallback containment. Portable tests cover abstract classification and cleanup
ordering, but do not inject failures through the Win32 adapter.
