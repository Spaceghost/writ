# Exploratory registryRead comparison implementation

A fixed no-data child could produce different initialization statuses with and without a registryRead capability. The reviewed [design](exploratory-registryread-ab-design.md) proposes an exploratory ABBA sequence; this implementation is untested on Windows and does not establish a cause, environment equivalence, or worker confinement.

The separate branch-only workflow builds the fixed child, ordinary controls, ABBA observer and five named synthetic tests on a fresh disposable Windows runner. It records source and binary hashes, checks child PE imports, and stops on a failed test, unexpected result, timeout, or uncertain cleanup. It uses the trusted runner's `RUNNER_TEMP` for its fixed paths; a standalone caller can change that environment variable, so its no-data path guarantee applies to the controlled workflow. The temporary exact-ref guard and job are dispatch scaffolding and must be removed before integration. The separately reviewed first run and its exact observations are preserved in [run 42322440747](run-42322440747/README.md).

The observer uses one fresh package, fixed no-data child and one report pipe, and checks the selected actual token capability SID and full attributes in each arm. Its selected user, integrity, elevation, authentication LUID, group, restricted-SID and privilege fields are compared privately, excluding capabilities. Logs retain counts and capability attributes but not those raw fields: an independent reader cannot reconstruct the token sets, and the comparison is an observer assertion. It compares the constructed environment input bytes but does not independently inspect the child's environment. PSS is pre-resume only; loading and initialization can subsequently change the handle set. OS state, package state, ordering, shared caches and snapshot perturbation can affect observations, which therefore remain inconclusive.

The owned resources include the two arrays and returned SIDs from successful `DeriveCapabilitySidsFromName`, token and snapshot handles, private executable, attributes, four package WFP filters, fresh profile, child job and process. The OS owns the returned pointer validity guarantee; count, null and SID shape are bounded and unexpected outputs are incomplete. Shared WFP/profile are retained when a child's exit is unverified; the disposable VM is then the fallback boundary, not verified in-guest cleanup. `CoTaskMemFree`, `FwpmFreeMemory0` and `DeleteProcThreadAttributeList` report no status. The diagnostic-only WFP installer retains a successfully opened session for checked cleanup, checks transaction abort status, and adopts filter IDs only on success; any shared setup failure remains cleanup-unverified. Selected token preparation can report a semantic-or-API unknown when its bounded helper fails; it is not presented as a raw denial. The native adapter error and cleanup branches have not been fault-injection tested. The portable classifiers do not establish Windows API behavior, package isolation, network denial, or equivalence to the strict byte worker.
