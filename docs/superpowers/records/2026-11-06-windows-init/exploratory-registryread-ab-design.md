# Proposed exploratory no-data registryRead A/B observation

Status: design only, awaiting independent review. No A/B launcher, test or native run has been implemented or executed. The actual byte-worker profile and strict Windows gate remain unchanged. Because the complete child environment is not independently read before resume, even a repeatable A/B difference is **inconclusive as proof of a one-factor cause**.

In [run 42319102323](run-42319102323/README.md), two separate zero-capability, Win32k-disabled no-data LPAC children each had a one-value pre-resume PSS observation and then returned Winsock `10107`, USER32 load error `1114`, and OLE32 load error `1359` in that same process lifetime. Ordinary no-data controls returned zeros. The existing older `registryRead` diagnostic also enabled Win32k and had different job limits, so it cannot tell us which configured difference matters. The smallest useful next observation is an A/B test of the named `registryRead` capability while attempting to hold other **observed** launch controls fixed. The capability name alone does not establish which Windows resource causes any error.

## Fixed no-data trial

On one fresh disposable Windows runner with no Writ mount, policy pipe, session, public fixture, protected bytes or real worker, launch only a fixed diagnostic child. The observer accepts no caller-selected image, process, command, handle, input data or destination. The child receives exactly one private report-pipe writer in the explicit inheritance list; an excluded synthetic event is a numeric-value negative control. Use the same pinned executable and hash, exact fixed initialization code and bounded report/EOF protocol as the same-lifetime slice. No socket or traffic probe, clipboard call or COM activation is introduced. The held parent pipe must match the sole captured child handle before resume; a PSS snapshot is **pre-resume only**, does not prove later handles and may itself perturb the diagnostic.

Create one fresh, supervisor-owned diagnostic LPAC package for this trial and keep it until every case retires. Do not reuse a real worker's package or map any case to a Writ actor. Launch sequential independent children in order **A B B A** with ordinary no-data positive controls before and after:

| Arm | Token capability SIDs | Win32k system calls |
| --- | --- | --- |
| A | none | disabled |
| B | exactly one enabled `registryRead` SID | disabled |

Each child has its own retained process handle, PID/creation time, kill-on-close LPAC job and report pipe. Retain identical observed child-job flags and configured memory, active-process, child-process, UI and mitigation limits, user/logon facts, LPAC opt-out and package SID; verify the observer-only budget and that the child is outside it but inside its LPAC job. Check the original package's four owned WFP blocks before every case and do not change them during the trial. Check the same fixed image digest and process/fixture lifetime. A PSS snapshot, exact report framing and a successful cleanup are required for **each** case. Failure to set or read back B's exact enabled capability, or an unexpected capability, is incomplete; do not fall back to a broader token or relaxed Win32k.

The current `writ_worker_create` creates a fresh profile per call and hard-codes the zero-capability profile. A shared-package A/B sequence therefore needs **new diagnostic-only launch/resource code**, not a change to that helper, the production policy path or any real worker. Before implementation, review how the fresh package, private image, owned WFP session and process/job resources remain owned across sequential cases without exposing bytes. If equivalent checked setup or safe resource lifetime cannot be established, stop and preserve the gap. Neither the `registryRead` child nor any other diagnostic child may receive Writ authority or caller-supplied, fixture or protected Writ data, handles or paths. Windows DLL and provider initialization may still consult OS configuration or registry state; the diagnostic must not capture or log its contents.

## Comparison controls and uncertainty

Derive the `registryRead` SID from the platform and independently read the actual token's capability list: A must have zero capability SIDs; B must have exactly the one derived SID with its enabled attribute. Record and compare bounded canonical token group, restricted-SID and privilege sets/attributes, user SID, authentication LUID, low-integrity, elevation and LPAC AccessCheck results; per-process token IDs, PIDs and creation times are distinct and are never treated as identity equality. Record configured job/UI/child/Win32k facts, parent budget membership, WFP filter identities and fixed image hash. If any unintended or unreadable difference appears, label the pair incomplete or inconclusive rather than claiming one-factor equivalence.

[DeriveCapabilitySidsFromName](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-derivecapabilitysidsfromname) returns two separately allocated SID arrays. Trust only allocations returned by the OS on documented success; require bounded counts (proposed group cap 16 and capability count exactly 1), non-null arrays/entries when required, and well-formed SID checks before use. These checks do not make arbitrary or attacker-controlled pointers safe; unexpected output is incomplete. Its documentation requires `LocalFree` for each returned SID and each array; check every applicable free as well as all owned token/query handles and attribute-list allocations. If returned counts or pointers cannot be safely validated or bounded, do not perform an unsafe walk or claim cleanup; mark incomplete and use the disposable VM as fallback. The documentation does not specify usable output ownership on API failure: do not assume returned values are valid or blindly free/iterate them; record unverified cleanup unless a documented contract is established. These handling paths need focused synthetic and native review before any run.

The supervisor may compare the explicitly constructed synthetic environment inputs privately, without logging values or paths, but that input is not an independent readback of the suspended child's complete environment. A child self-report after resume would be a separate, potentially perturbing observation and must not be substituted. Consequently every A/B inference remains inconclusive as a strict controlled comparison even if the recorded facts otherwise match. Per-package caches, registry/OS/provider state, case order and background activity can also vary; ABBA repetition can expose some drift but cannot eliminate those confounders. A positive or negative change may guide a later investigation; it is not proof that registry access or any other mechanism caused the error.

For each child, while suspended take only the bounded PSS handle-value snapshot, require a complete walk/count match and the known one-pipe object comparison, then free/check the marker and snapshot and close/check the parent writer. Resume the retained original thread exactly once only after all gates pass; `ResumeThread` must report previous suspend count exactly 1. Require that same child to exit within the deadline and produce exactly one complete fixed-size report followed by EOF, with module-state/cold-load and initializer cleanup checks. Keep raw initializer errors as observations; never classify `10107`, `1114`, `1359` or other initialization failures as access denials. If snapshot, launch, token, report, timeout or cleanup is incomplete, stop the entire sequence and retain the failure.

## Cleanup and review prerequisites

Keep the one owned WFP session and private package resources until all children are observed retired; never remove filters while a child may remain live. Check per-case PSS objects, duplicates, process/thread/job and pipe closure. After the final child, close only this trial's dynamic WFP session and verify its four recorded filter IDs absent via a separate readback engine, then delete only its owned private image/directory and package profile. Any unverified teardown, timeout or launcher failure that erases ownership state stops further cases; disposable VM destruction is fallback containment, not proof of successful cleanup. Bound the observer's memory/CPU and external wall time; unmeasured PSS kernel-internal allocation and abrupt-parent cleanup remain limitations.

Before any native run, require independent review of the diagnostic source, source/trust inventory and an exact-ref-only disposable-runner workflow. Portable and Windows synthetic tests must cover capability-set/count/attribute mismatch, token and job drift, PSS limits and malformed walks, positive one-pipe object comparison, previous suspend counts 0/1/>1/error, report truncation/trailing/open-writer, timeout and each cleanup failure. Pure classification tests must not be described as native adapter fault injection; missing injected paths remain explicit. Retain build, hashes, raw bounded reports, case order, control results and cleanup outcomes. Exclude temporary workflow guards from master integration. No run is authorized by this design.

The strongest future conclusion is that specific no-data children under recorded A/B configurations produced the recorded initializer results. No outcome changes the real byte-worker failure, proves a Windows root cause, establishes independent environment equality or earns confinement or host-qualification credit.
