== Attempt 1: runtime options that shrink the reservations ==
None exist. The generated C's option parser (gen/hello.c main, lines 2996-3065) accepts exactly
--help, --gpu-build, --threads N and --gpu on|off|<size>, plus BENDRTS; its help text
(CLI_HELP, hello.c:295-301) lists the same four, and `bend guide` documents only
`+RTS --threads 8` and `+RTS --gpu 4GB` ("cap the GPU heap"). The CPU heap size is fixed:
corpus_setup computes `(!gpu ? 1ull << 33 : bytes != 0 ? bytes : gpu_span())` (hello.c:2257), and
for this program gpu is false (BANGS == 0, so `--gpu <size>` sets `mem` but not the CPU span;
matrix E2/E10 ran `--gpu 64MB` and still reached `reservation failed`). The stack is fixed at
`1ull << 31` + 16 KiB + 4*SIGSTKSZ (pool_stack, hello.c:1667-1670). Shrinking either means editing
the generated C or the runtime, which the plan forbids. Not run again here (E10 already ran
--gpu 64MB and BENDRTS); outcome: no option to try.

== Attempt 2: the platform's memory configuration raised ==
The only linuxu memory option in 0.16.3 is LINUXU_DEFAULT_HEAPMB
(plat/linuxu/Config.uk:14-21, `int "Default heap size (MB)"`, default 4; the help says it can also
be set at run time as linuxu.heap_size through uklibparam). There is no mmap limit option.
How it is used (plat/linuxu/setup.c):
  51  #define MB2B (1024 * 1024)
  53  static __u32 heap_size = CONFIG_LINUXU_DEFAULT_HEAPMB;
  54  UK_LIB_PARAM(heap_size, __u32);
  62  __u32 len;
  65  len = heap_size * MB2B;
  72  pret = sys_mapmem(NULL, len);    // syscall.h:201-203: host mmap, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS
The length is a 32-bit unsigned product, so the platform heap is at most 4095 MiB, and any
setting of 4096 or more wraps modulo 4 GiB (the run-time linuxu.heap_size goes through the same
__u32 multiplication, so enabling uklibparam cannot help). That heap is the only
UKPLAT_MEMRT_FREE region handed to the allocator (lib/ukboot/boot.c:207-226).
Builds changed (reason: attempt 2, raise the platform heap): CONFIG_LINUXU_DEFAULT_HEAPMB 4 -> 4095
(the largest value whose byte length fits __u32) and 4 -> 8196 (to confirm the wrap).
  HEAPMB 4095, T=60: status 124; output after the banner: `bend: reservation failed`.
    /proc maps while hung: 7f183a200000-7f193a100000 rw-s 4095 MiB /dev/zero (deleted); VmSize 4194428 kB, VmRSS 1096 kB.
    The host granted the whole 4095 MiB heap; the runtime's 8 GiB request is still more than twice it.
  HEAPMB 8196, T=60: status 124; `bend: reservation failed`.
    /proc maps while hung: a 4 MiB /dev/zero mapping; VmSize 5244 kB. 8196 MiB wrapped to 4 MiB, as the source reads.
Outcome: the platform heap cannot be made as large as one 8 GiB reservation, let alone the
8 GiB heap plus the 2 GiB stack the runtime takes next.

== Attempt 3: can linuxu's mmap honour an 8 GiB MAP_NORESERVE request? ==
No, by reading the 0.16.3 source; the runs above agree.
- posix-mmap cannot be configured on linuxu: lib/posix-mmap/Config.uk:4 `depends on LIBUKVMEM`;
  lib/ukvmem/Config.uk:7 `select PAGING`; plat/Config.uk:84-86 HAVE_PAGING `default y if PAGING`;
  plat/linuxu/Config.uk:5 `depends on !HAVE_PAGING`. This is why the Kraftfile's
  CONFIG_LIBPOSIX_MMAP is dropped.
- The mmap that is linked is lib/ukmmap (implied by lib-musl, libs/musl/Config.uk:7
  `imply LIBUKMMAP`; LIBUKMMAP=y in .config). Its mmap (lib/ukmmap/mmap.c:67-121) never calls the
  host: it rejects fd != -1, accepts MAP_NORESERVE only as one of the flag combinations it checks
  (line 86), then takes `uk_memalign(uk_alloc_get_default(), __PAGE_SIZE, len)` (line 98) from the
  platform heap and `memset(mem, 0, len)` (line 112). So a MAP_NORESERVE request is served as an
  eager, zeroed allocation from a heap of at most 4095 MiB; there is no lazily backed or reserved
  path. The address hint is honoured only if it already lies inside an earlier ukmmap region
  (lines 89-96), so the runtime's high-base hints all fall through to the allocator.
- Observed: every one of the 13 requests returned -ENOMEM (-12) from uk_syscall_e_mmap.

== Which attempt came closest ==
Attempt 2 with HEAPMB 4095: the largest heap linuxu can map (4095 MiB, granted by the host), still
under half of the runtime's first 8 GiB reservation. No attempt reached the stack reservation,
the event loop, or the first print. The remaining routes all fall outside this lane's rules:
editing the generated C or the Bend runtime to shrink `1ull << 33`, or patching Unikraft's
__u32 heap length or ukmmap.

== After the failure ==
err_fail calls _exit(1) (hello.c:522-526), but the process does not end: in every run it is still
alive when `timeout` kills it (124), as in the matrix (E10). Why linuxu's _exit does not end the
process was not traced. A harness can only tell this failure by reading the output.
