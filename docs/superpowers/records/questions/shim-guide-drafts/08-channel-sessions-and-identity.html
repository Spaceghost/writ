Shim review 8 of 9: the Writ channel service, sessions, and route identity

When the component's config has a <writ_channel> node, the shim announces a service to its parent. Clients can then open Writ_channel sessions, which are routed by init. Each session gets two 4 KiB buckets (RAM dataspaces, one for requests, one for results) and a signal handler, all served on a dedicated entrypoint, writ_channel. The session interface (writ_channel_session.h:72-75) has four RPCs, and each only hands over a capability or registers one. The security-relevant step is at session creation. init prefixes every session label with the requesting child's name, so the client cannot forge that prefix. The shim looks the label up in the integrator's <policy> nodes and stores the matching subject number with the channel. Bend later maps that number to an identity (GB-007). Read the header 1289-1333 first. See INVENTORY.md:177-200 and :212-217.

Open: writ_mem.cc:1289-1333, writ_mem.cc:1402-1476, writ_mem.cc:1521-1667

Excerpt, writ_mem.cc:1532-1553 (tabs shown as four spaces):

    /*
     * The subject word of the <policy> under <writ_channel> that matches
     * the label best, 0 for none. Only a policy that names the label or a
     * label prefix counts: the parent sets the prefix, while a suffix is
     * the client's own choice and must not bind identity. The config is
     * libc's, never updated, so every session sees the same policies.
     */
    uint32_t _subject(Session_label const &label)
    {
        uint32_t subject = 0;
        _channel_libc_env->with_config([&] (Node const &config) {
            config.with_optional_sub_node("writ_channel", [&] (Node const &policies) {
                subject = with_matching_policy(label, policies,
                    [&] (Node const &policy) -> uint32_t {
                        if (!policy.has_type("policy")) return 0;   /* <default-policy> */
                        if (!policy.has_attribute("label")
                         && !policy.has_attribute("label_prefix"))
                            return 0;                               /* suffix-only */
                        return policy.attribute_value("subject", uint32_t(0)); },
                    [&] () -> uint32_t { return 0; }); }); });
        return subject;
    }

Limit or policy? This is the section a reviewer is most likely to call policy. _subject encodes a security rule in C++: a <default-policy> or a suffix-only policy does not bind identity, because a label suffix is chosen by the client (1546-1549). _create_session then denies the session (1575-1579). The case for "binding": the shim decides no grant. It only looks up a word the integrator wrote, applies the same rule to every label, and leaves every request's accept or deny to Bend. The case for "policy": who may hold a channel, and under which subject, is an authority fact established here, outside Bend. MAX_CHANNELS (8) and the quota check are capacity bounds.

Confirm by reading:

  1. The subject stored on a channel comes only from the integrator's config, matched against the parent-prefixed label: _create_session reads only the label and ram_quota from the client's arguments writ_mem.cc:1557-1559 and takes the subject from _subject (1574).
  2. A <default-policy>, a policy with only label_suffix, no match, or subject="0" all give subject 0 writ_mem.cc:1546-1551, and subject 0 is DENIED writ_mem.cc:1575-1579.
  3. Apart from claim 2, a session is refused only for capacity: ram_quota below CHANNEL_SESSION_RAM (1559-1564), or no free slot, where a closing slot stays taken until Bend has taken its close event writ_mem.cc:1581-1593.
  4. The four RPC methods writ_mem.cc:1467-1475 return the two bucket capabilities and the request signal, or store the client's result signal; none reads a bucket or decides anything.
