== Mechanism (Unikraft 0.21.0, commit 7351f8b563c9e6773da9fdd5bacde6ac91e32112) ==

Hook source: hosts/unikraft/exit_device.c (sha256
b1dc08bbf14f88a998c22fa64da37e56113c08142d742559a419ee338e1bc51e at Task 1; Task 2 edited
only its header comment, adding boot.c:447/452 and crash.c:129/132 citations, comment-

hosts/unikraft/INVENTORY.md. It is linked by REFERENCE (not copied): the app Makefile.uk
names its path in this worktree. Paths below are under $W/src/unikraft.

1. Termination table. include/uk/init.h:67 (struct uk_term_ctx { target; exit_code; }),
   :78 (uk_term_func_t), :118 (uk_early_initcall_prio). lib/ukboot/boot.c:426 the init
   thread waits on the shutdown barrier; :447 calls every term function in reverse table
   order with &tctx; :452 uk_pm_shutdown(tctx.target). exit_code is main's return
   (boot.c:533) or, after exit()/_exit(), the init process's stored status
   (lib/posix-process/exit.c:203 'exit_status & 0xff'; copied into the context by
   lib/posix-process/shutdown.c:103, a late-class term registered at :127 that runs
   before ours). The hook registers class 1 priority 0 (inittab section .uk_inittab10),
   so it is the last term function, immediately before uk_pm_shutdown.
   Written value: the status if 0..0x7c; 0x7f if the status is above 0x7c ("not
   representable"); 0x7d if tctx.target is not SYSHALT (an init failure or a restart
   request). QEMU then exits (v << 1) | 1.
2. Process exit event. lib/posix-process/include/uk/process/events.h:287
   (POSIX_PROCESS_PPEXIT_HANDLER), raised at lib/posix-process/exit.c:213 after the status
   is stored. On the init process (pid 1, lib/posix-process/process.h:36 UK_PID_INIT) the
   handler calls uk_boot_shutdown_req(UK_PM_SHUTDOWN_OP_SYSHALT)
   (lib/ukboot/include/uk/boot.h:57), which releases the barrier in step 1.
3. Crash event. lib/ukdebug/include/uk/crash.h:106 (UK_CRASH_EVENT), raised at
   lib/ukdebug/crash.c:129 after the crash screen and before crash_shutdown() (:132; with
   the default LIBUKDEBUG_CRASH_ACTION_HALT, lib/ukdebug/Config.uk:48, that is
   uk_pm_syscrash() at crash.c:79). The handler writes 0x7e, so QEMU exits 253 before
   Unikraft's own crash action runs. The crash event is the supported crash hook; no
   Kconfig change was needed. Without the device the crash action is Unikraft's own
   (Task 2 observes halt versus reset).

== Limits ==

- QEMU's exit status is (v << 1) | 1 truncated to 8 bits: always odd, 128 values. The
  hook passes program statuses 0..124 through (QEMU 1..249) and maps 125..255 to 0x7f
  (QEMU 255), so those statuses are not distinguished from one another. 0x7d (QEMU 251,
  non-halt shutdown) and 0x7e (QEMU 253, crash) are written only by the hook, never for
  a program status.
- IO.die(Unit, 1, "die") and a runtime failure (err_fail -> _exit(1), e.g. '+RTS --threads 0';
  arena exhaustion would take the same path by reading the emitted C, not induced) both
  give status 1, QEMU 3. They are distinguished only by the console text, which is
  diagnostic, not a status. A distinct runtime-failure code needs a runtime change or a
  host twin, outside this task.
- The crash value says only "Unikraft crash". The runtime's own fault message
  ('bend: memory fault ...') still does not appear (matrix E4); the stack-guard page
  fault, guest-RAM exhaustion by stack growth, and any other unhandled trap all give 253.
- QEMU 0 or 124 is now never success; only 1 is. A harness without the device sees the
  old behavior (0 for return from main; crash action per Task 2).
- One CPU, cooperative scheduler, +RTS --threads 1. Exit from a second lane, and exit
  while other posix threads are running, were not tried.
- Whether LIBUKBOOT_MAINTHREAD's own main_thread_dtor would end an exit() run without
  the ppexit handler was not tested; gdb shows the handler's request comes first.
- -no-reboot was used on every run; reset versus halt after a crash without the device
  is Task 2's observation (verification/unikernel-crash-action.txt: a power-off, QEMU 0,
  no reset).
- abort() and signal termination (SIGABRT, a raised or unhandled signal) were not
  tested. A Bend program cannot call abort(), and the runtime's own failures go through
  err_fail -> _exit(1); whether an abort() in C reaches the ppexit handler (and so the
  status path) or Unikraft's crash path is unknown.
