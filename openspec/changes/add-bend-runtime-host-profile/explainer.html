Why this shape

The founding chat said two things about the unikernel: "wrap it in an existing one" first, and the real value is being able to "rebuild from entirely new hardware" so that data-theft recovery takes moments. The existing roadmap already had a Drift kernel host at the far end of the host lane, but every host change (Genode, Windows, Drift) contained the same unexamined task: "port the Bend runtime." Nobody had written down what that runtime needs.

So the lane is split into a prerequisite everyone shares, the cheap wrap-it route, and the expensive own-kernel route. Each is a separate OpenSpec change with its own requirements and evidence, matching how Spaceghost structured the seven feature changes he landed yesterday.

The three changes, in order

1

add-bend-runtime-host-profile

A per-Bend-version inventory of what the generated C needs from its host, a monitor profile allowlist of symbols and effects, a build-time check of the produced binary, and a parity rule that one lane and four lanes give identical decisions.

feeds → every host port · genode 1.2 · windows runtime · drift 1.3 · changes 2 and 3 below
2

add-unikernel-appliance-host

Boot the unmodified Bend monitor binary inside an existing Linux-ABI unikernel. Immutable reproducible image, one authenticated ingress, state kept outside the image, a timed rebuild drill. Explicitly not a worker confinement boundary.

depends on → 1 for the corpus milestone · host contract, grant issuance, durable publication for the service milestone
3

add-freestanding-bend-runtime

A no-libc host layer under the unchanged evaluator for the Drift kernel route. 64-bit first. Serial-captured corpus parity with the Linux single-lane record.

depends on → 1 · feeds → add-drift-kernel-host task 1.3 only; supplies none of that host's isolation evidence

Change 2 is the fast path to something bootable. Its first milestone needs only change 1 and a QEMU. Change 3 is research-grade and sits behind Drift's kernel work. Doing them in this order means the unikernel can ship evidence while the kernel route is still being argued about.

What the Bend runtime actually asks of a host

This is the inspection behind change 1, from emitting C for a one-line IO.print program with Bend 2.0.39. The emitted file is 3,074 lines; the lower half is the runtime. It is recorded in docs/BEND-RUNTIME.md.

The useful discovery: effects are registered per program through constructor functions that fill a table. A monitor using only IO.print and IO.die links no socket, file, audio, or process code. An unregistered effect fails with the runtime's own "an alien request" error. That is what makes a tight monitor allowlist practical rather than aspirational.

1 · Bend runtime host profile

Eight requirements, sixteen scenarios. The point is to replace "port the runtime" with a checklist a host can pass or fail.

RH-001Inventory is pinned to a Bend version; a compiler migration makes every host qualification stale until re-reviewed.
RH-002The monitor profile is an allowlist: memory, faults, threads, clock, loop, process, atomics, plus IO.print, IO.print_err, IO.now, IO.sleep, exit, and a host-added authenticated channel. Sockets, files, spawning, audio, windows, GPU loading are denied.
RH-003The actual produced binary is checked (undefined symbols or effect table). A passing run log alone does not qualify.
RH-004Primitives keep runtime semantics. A clock that can go backward fails even if every test passes.
RH-005Lane count does not change decisions: --threads 1 and four threads print identical PASS lines and the same 638 count.
RH-006Faults fail stop. A host that swallows the signal or resumes after it is out of profile.
RH-007CPU fallback is recorded as CPU. Never as GPU.
RH-008Evidence is stored per host and separated into executed versus review-only.

Tasks: an inventory command, the allowlists, the binary check (shown failing on a binary that links TCP.listen), the single-lane parity run, forced fault and reservation failure, and updating the other host changes to cite it.

2 · Unikernel appliance host

Ten requirements, twenty scenarios. The appliance is the monitor and nothing else, in an image you can name by hash and rebuild from zero.

UA-001Image contains only the monitor binary, the unikernel, and boot config. A debug shell disqualifies it.
UA-002Two clean builds from pinned inputs give the same image hash; deployments name images by hash.
UA-003The library corpus and four examples run inside the booted image and match the Linux record line for line.
UA-004The single address space is not a worker boundary. Running requester code inside is denied, not sandboxed.
UA-005Exactly one ingress: the host contract's authenticated session channel, plus the durable store connection.
UA-006Session, ledger, epochs, and sealed artifacts live only in the attached durable store. The image holds nothing that must survive replacement.
UA-007Rebuild is drilled and timed: destroy, boot fresh image on a fresh VM, attach store, reconcile each outstanding invocation exactly once. Repeated for every image change.
UA-008Monotonic clock verified at boot; missing clock denies protected work, missing entropy denies challenge issuance.
UA-009The trusted base is named: hypervisor, host kernel, firmware, unikernel. "Immune to host compromise" is rejected as a claim.
UA-010QEMU emulation, hardware virtualization, and physical deployment are separate evidence.

The "no Linux zero-day" line from the chat is kept, but scoped: the guest has no Linux kernel, so a Linux kernel bug on the host does not execute inside the monitor. The hypervisor and host still have to be trusted, and the record has to say so.

Milestones in the tasks: boot the corpus on two candidate unikernels and pick one by evidence; reproducible image; corpus passes under QEMU; single ingress verified by scanning; empty-store and populated-store boots; clock and entropy denials; the rebuild drill with elapsed time.

3 · Freestanding Bend runtime

Nine requirements, eighteen scenarios. This is the piece the Drift kernel host was missing: how you run the evaluator with no libc at all.

FR-001The generated evaluator and effect table are linked unmodified; only a host layer is added beneath. Patching the evaluator disqualifies the port.
FR-002First port is x86_64 long mode. A 32-bit build is refused with the term width as the reason.
FR-003Memory is a fixed arena with a guard region; exhaustion halts with the runtime's own message.
FR-004Faults halt with a distinct code. No resumption.
FR-005Single-lane parity: serial capture equals the Linux --threads 1 --gpu off record line for line.
FR-006Clock is calibrated monotonic or reported absent; absent denies deadline-dependent checks.
FR-007Only monitor-profile effects link: console to serial, exit to the emulator's exit device. Alien effects halt.
FR-008! calls run on the lane pool and are recorded as CPU.
FR-009Results are emulated evidence and count only toward the Drift host's runtime task, not its isolation tasks.

The design replaces each libc dependency one for one: mmap becomes an arena, signals become an exception handler that halts, pthreads become a single lane (kernel threads later, behind the same symbols), the clock becomes a calibrated TSC, the self-pipe becomes an in-memory completion queue. The evaluator never knows.

The static link result matters because that is exactly what a Linux-ABI unikernel consumes. The Drift result is a real blocker for change 3 on this machine and is recorded as such, not papered over.

Open decisions

  • Which unikernel. Nanos runs a single process with threads and consumes plain ELF. Unikraft's ELF loader needs position-independent executables and describes binary compatibility as not yet upstreamed. The proposal makes this a task outcome, chosen by booting the corpus on both. If you already have a preference, say so and it becomes a decision instead.
  • 64-bit kernel variant for Drift. Change 3 asserts the first port must be long mode. That means adding an x86_64 boot path beside Drift's 32-bit example, which is Drift work, not Writ work. Spaceghost should weigh in.
  • Where the inventory script and binary check live. AGENTS.md keeps authored implementation in Bend. A symbol-allowlist checker is build tooling like OpenSpec. The proposal puts it in build tooling; the exact directory is unnamed.
  • Provisioning path for channel identity and entropy. UA-006 says the image holds no secret that must survive rebuild, so keys arrive at boot. How is out of scope and will need its own change.
  • Drift kernel failure on this machine. Someone needs to try an older GCC or QEMU to see whether it is a toolchain regression or a real bug.

What implementing change 1 would look like

If the shape is right, the first real work is small and self-contained:

# 1. a command that regenerates the inventory
bend tools/inventory/Hello.bend -o build/hello.c
grep -oE '\b(mmap|pthread_[a-z_]+|clock_gettime|...)\(' build/hello.c | sort -u

# 2. a binary check against the monitor allowlist
nm -u build/tests-native | awk '{print $2}' | sort > actual.txt
comm -23 actual.txt tools/profile/monitor-symbols.txt    # must be empty

# 3. the parity run
build/tests-native +RTS --threads 1 --gpu off | diff - verification/tests-native.txt

Those three artifacts, plus a forced stack overflow and a forced reservation failure, close most of change 1's tasks and give change 2 its starting binary.
