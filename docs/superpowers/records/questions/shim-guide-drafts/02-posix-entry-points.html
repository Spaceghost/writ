Shim review 2 of 9: the three libc replacements (mmap, munmap, mprotect)

These are the public POSIX entry points the Bend runtime calls. The program binary's definitions shadow libc's by ordinary symbol interposition (INVENTORY.md:50-55, "How the entry points win"). The shim takes over only one shape of request: an anonymous, private, read-write mapping of at least 1 GiB. That is how the Bend runtime reserves its 8 GiB term heap and its 2 GiB per-lane stacks. Everything else goes to libc unchanged. The question for this page: does any refusal here depend on who is asking or what the memory is for, or only on whether the shim can carry the request out exactly? The inventory's "Exported symbols" table (INVENTORY.md:73-88) states the behaviour you are checking.

Open: writ_mem.cc:907-914, writ_mem.cc:1031-1137

Excerpt, writ_mem.cc:1041-1071 (tabs shown as four spaces):

extern "C" void *mmap(void *addr, ::size_t len, int prot, int flags,
                      int fd, ::off_t offset)
{
    if (!_env || !_libc_mmap) { errno = ENOSYS; return MAP_FAILED; }  /* before construct */

    if (!_qualifies(len, prot, flags, fd, offset))
        return _libc_mmap(addr, len, prot, flags, fd, offset);

    Mutex::Guard guard(_mutex());
    return _reserve(addr, len);
}

extern "C" int munmap(void *addr, ::size_t len)
{
    if (!_env || !_libc_munmap) { errno = ENOSYS; return -1; }  /* before construct */

    addr_t const a = addr_t(addr);
    {
        Mutex::Guard guard(_mutex());
        for (Reservation &r : _res) {
            if (!r.used || !_overlaps(a, len, r.base, r.size)) continue;
            /* only the whole reservation can be unmapped */
            if (a != r.base || len == 0 || len > r.size
             || _page_round(len) != r.size) {
                errno = EINVAL; return -1; }
            _release(r);
            return 0;
        }
    }
    return _libc_munmap(addr, len);
}

Limit or policy? Each refusal here is "this unit cannot do that exactly": partial munmap (1063-1065), any protection other than RW or NONE, and lifting a guard (1108, 1112-1113) are unsupported operations, not judgments. MAX_GUARDS (1114) is a fixed table size. One place returns success without acting: RW on a guard-free range returns 0 (1105-1110), because a reservation is already RW. Decide whether you accept that as faithful.

Confirm by reading:

  1. _qualifies writ_mem.cc:907-914 tests only the request's shape (length, prot, flags, fd, offset); it reads no caller identity, label, or Bend state, and a non-qualifying call is forwarded unchanged to libc at 1046-1047.
  2. munmap releases only a whole reservation: an overlapping range that is not exactly the reservation is EINVAL writ_mem.cc:1063-1065; a range overlapping no reservation goes to libc (1070).
  3. mprotect on a reservation either records a PROT_NONE guard (1116-1121) or fails with ENOTSUP/ENOMEM/EINVAL writ_mem.cc:1092-1114; the single silent success is RW on a range with no guard (1105-1110).
  4. If re-attaching the pieces around a new guard fails, the guard stays recorded and the call returns ENOMEM writ_mem.cc:1124-1135; the shim never drops the guard to save the data.
