Shim review 4 of 9: charging a chunk on first touch

When the program first touches an untouched 2 MiB chunk of a reservation, the fault path (pages 5 and 6) calls _populate. It allocates a 2 MiB RAM dataspace from the component's own PD, which charges the component's RAM quota, and attaches it into the reservation's region map in "pieces" that skip any guard range. Two details matter for GB-006. Allocation goes through a plain Pd_session_client (557, built at 1893 on pd_session_cap()), not Env::pd(). The Env::pd() client turns an out-of-quota error into a blocking request to the parent for more resources. So a fault either succeeds from the quota the component already has, or is refused. On base-hw, attaching a piece costs metadata in core that is charged to the RM session's own small quota, so the shim may upgrade that session. An upgrade moves some of the component's own quota into the session; it is not a request for more. Header 153-189 explains this; INVENTORY.md:92-120 (RM) and :132-136 (PD) list it.

Open: writ_mem.cc:153-189, writ_mem.cc:543-673

Each claim below shows the lines that carry it (line number, tab, source; tabs in the source shown as four spaces), what I see there, and my recommendation. Nothing is pre-selected: read the lines and choose.

Claim 1

_populate refuses with a named reason, before allocating, when the PD's available RAM is below the chunk plus RAM_MARGIN or its caps are below CAP_MARGIN. The allocation goes through the plain _pd client, not Env::pd().

648	    Pd_session::Stats const st = _pd->stats();
649	    if (st.ram.avail().value < len + RAM_MARGIN)

651	    if (st.caps.avail().value < CAP_MARGIN)
652	        return "chunk could not be charged: cap quota";
653	
654	    Ram_dataspace_capability ds { };
655	    char const *err = nullptr;
656	    _pd->alloc_ram(len, CACHED).with_result(
657	        [&] (Ram_dataspace_capability cap) { ds = cap; },
658	        [&] (Alloc_error e) {
659	            err = e == Alloc_error::OUT_OF_CAPS ? "chunk could not be charged: alloc_ram OUT_OF_CAPS"
660	                : e == Alloc_error::OUT_OF_RAM  ? "chunk could not be charged: alloc_ram OUT_OF_RAM"
661	                :                                 "chunk could not be charged: alloc_ram DENIED"; });
662	    if (!ds.valid()) return err ? err : "chunk could not be charged: invalid dataspace";

What I see. The margin checks (648-652) come before alloc_ram (656), and every error is named. _pd is a plain Pd_session_client (557, built on pd_session_cap() at 1893), so an out-of-quota allocation returns an error and never becomes a blocking resource request. The margins are fixed Genode quota bookkeeping (keep 64 KiB and 8 caps free for the rest of the component), not Writ budget accounting. A reviewer could still call "keep 64 KiB back" a host resource rule; it is compile-time and the same for every fault.

Recommendation: Confirmed, the checks precede the allocation and use the plain client.

_upgrade_rm_session acts only on OUT_OF_RAM/OUT_OF_CAPS, only if the PD keeps its margins after the transfer, with fixed amounts; _attach_pieces allows at most RM_UPGRADE_ATTEMPTS (4) upgrades per piece, and every upgrade sent or declined is counted.

What I see. As stated: fixed amounts (8 KiB or 2 caps), the margin test, and the counters. With attempt < 4 a piece gets at most 4 upgrades, so 5 attach tries. The upgrade is a session upgrade sent to the parent (Env::upgrade, header 166-174) and paid from the component's own quota, so it does not ask for more resources. Recommendation: Confirmed, the bound, the margins, and the counters are all in these lines.
