Unikernel port lane, Task 2: the platform action after a crash (halt versus reset)
Recorded 2026-11-03 on Linux x86_64 (Manjaro, kernel 7.2.9), no root.

Every run is an EMULATED BOOT under QEMU 11.1.2 with TCG (-accel tcg), machine type the
qemu-system-x86_64 default (pc), -cpu max, -m 4096 for Overflow (-m 1024 for Hello),
-append "+RTS --threads 1 --gpu off", 60 s timeout, serial captured whole. CPU only.
Unlike Task 1, the runs below DO NOT pass -no-reboot (except where stated). Unikraft
0.21.0 (7351f8b), kraft 0.12.16; pins in verification/unikernel-pins.txt. W is the build
workspace (realpath of ../writ-unikernel from the repository root); nothing built is in
the tree.

== Result ==

The crash is NOT followed by a reset. Observed, without -no-reboot:
- With the Task 1 hook and the debug-exit device: QEMU exits 253 right after the crash
  screen, before any reset (one banner, one program start).
- With the hook left out at build time (and, separately, with the hook linked but the
  device absent): Unikraft's own crash action runs and QEMU exits 0, consistent with a
  guest ACPI power-off (with a device at 0x501 the same image exits 85, qemu_crash's code). The banner and 'overflow probe start' appear exactly once; no
  output follows the crash screen; QEMU ends on its own in 10.6 to 16.8 s, well inside
  the 60 s timeout. Not a reset and not an idle halt.
- Control (same no-hook image, no -no-reboot): a reset injected from the QEMU monitor
  (system_reset) at about 4 s DOES re-run the image: the banner and 'overflow probe
  start' appear twice, then the second run crashes and QEMU exits 0. So a reset would
  have been visible in the captures above, and none occurred.
- Return from main without -no-reboot: the Task 1 Hello image exits QEMU 1 with the
  device and 0 without it, one banner, 'hi' once: also no reset.

Harness rule (stated accordingly, docs/UNIKERNELS.md updated): on this kernel and QEMU
qemu/x86_64 platform neither a crash nor a return from main resets the guest, so
-no-reboot is not needed to stop resumption at the image level for those paths. The
Writ harness still passes -no-reboot on every run as a guard: any path that does request a
reset (a triple fault before the crash handler, a guest that sets
LIBUKDEBUG_CRASH_ACTION_REBOOT, a different platform driver) then ends QEMU instead of
re-running the program. The hook writes 0x7d for a non-halt shutdown target, so with
the device a restart request is QEMU 251, not a silent re-run. Success is QEMU 1 only.

== Why (source, Unikraft 0.21.0 under $W/src/unikraft; read, consistent with the runs) ==

lib/ukdebug/Config.uk:48 default LIBUKDEBUG_CRASH_ACTION_HALT (our .config: the default).
lib/ukdebug/crash.c:129 raises UK_CRASH_EVENT (the hook's handler, which writes 0x7e to
port 0xf4), then :132 crash_shutdown(), which with the halt action is uk_pm_syscrash()
(crash.c:79). lib/ukpm/pm.c:122 uk_pm_syscrash calls the platform's syscrash op:
plat/kvm/x86/qemu.c qemu_crash writes 42 with outw to port 0x501 (QEMU's default
isa-debug-exit iobase; QEMU 85 if a device is there), 1 to port 0x505 (pvpanic), then
the ACPI shutdown 0x2000 to port 0x604 (power-off). Note also qemu.c:79-80: syshalt AND
sysrestart are both qemu_exit (41 to 0x501, then the ACPI power-off), so on this
platform even a restart request powers off. Confirmation that the native path is
qemu_crash: the no-hook image with '-device isa-debug-exit,iobase=0x501,iosize=0x02'
(no -no-reboot) exits QEMU 85 = (42 << 1) | 1.

== Limits ==

- One crash kind: the Overflow stack-guard page fault, on one CPU. A fault that the crash
  handler cannot reach (for example a triple fault, which QEMU turns into a reset) was
  not induced; that is the case the retained -no-reboot guards.
- LIBUKDEBUG_CRASH_ACTION_REBOOT was not built or run; by reading qemu.c it too would
  power off on this platform (sysrestart = qemu_exit).
- What is observed for Unikraft's own crash path (and its halt path) is "QEMU exited by
  itself with 0, no reset, no idle", plus the 0x501 runs (85 crash, 83 halt) showing that
  Unikraft's qemu_crash / qemu_exit ran; that their last step, the ACPI write to 0x604, is
  what ends QEMU with 0 is read from the source, not printed. QEMU 0 is consistent with an
  ACPI power-off.
- abort() and signal termination were not exercised (a Bend program cannot call abort;
  see verification/unikernel-exit-codes.txt limits).
