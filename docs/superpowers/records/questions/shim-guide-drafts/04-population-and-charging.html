Shim review 4 of 9: charging a chunk on first touch

When the program first touches an untouched 2 MiB chunk of a reservation, the fault path (pages 5 and 6) calls _populate. It allocates a 2 MiB RAM dataspace from the component's own PD, which charges the component's RAM quota, and attaches it into the reservation's region map in "pieces" that skip any guard range. Two details matter for GB-006. Allocation goes through a plain Pd_session_client (557, built at 1893 on pd_session_cap()), not Env::pd(). The Env::pd() client turns an out-of-quota error into a blocking request to the parent for more resources. So a fault either succeeds from the quota the component already has, or is refused. On base-hw, attaching a piece costs metadata in core that is charged to the RM session's own small quota, so the shim may upgrade that session. An upgrade moves some of the component's own quota into the session; it is not a request for more. Header 153-189 explains this; INVENTORY.md:92-120 (RM) and :132-136 (PD) list it.

Open: writ_mem.cc:153-189, writ_mem.cc:543-673

Excerpt, writ_mem.cc:643-673 (tabs shown as four spaces):

static char const *_populate(Reservation &r, addr_t off)
{
    size_t const idx = off / CHUNK;
    size_t const len = _page_round(r.chunk_end(idx) - idx*CHUNK);

    Pd_session::Stats const st = _pd->stats();
    if (st.ram.avail().value < len + RAM_MARGIN)
        return "chunk could not be charged: RAM quota";
    if (st.caps.avail().value < CAP_MARGIN)
        return "chunk could not be charged: cap quota";

    Ram_dataspace_capability ds { };
    char const *err = nullptr;
    _pd->alloc_ram(len, CACHED).with_result(
        [&] (Ram_dataspace_capability cap) { ds = cap; },
        [&] (Alloc_error e) {
            err = e == Alloc_error::OUT_OF_CAPS ? "chunk could not be charged: alloc_ram OUT_OF_CAPS"
                : e == Alloc_error::OUT_OF_RAM  ? "chunk could not be charged: alloc_ram OUT_OF_RAM"
                :                                 "chunk could not be charged: alloc_ram DENIED"; });
    if (!ds.valid()) return err ? err : "chunk could not be charged: invalid dataspace";

    r.chunks[idx] = { ds, true };
    if (char const *why = _attach_pieces(r, idx)) {
        _detach_pieces(r, idx);
        _pd->free_ram(ds);
        r.chunks[idx] = { { }, false };
        return why;
    }
    _chunks_populated++;
    return nullptr;
}

Limit or policy? This page is "accounting" in the Genode sense, not the Writ sense. It checks the component's quota against fixed margins (649-652: chunk + 64 KiB RAM, 8 caps) and spends quota on at most four fixed-size RM upgrades per piece (570-572, 620). Those are bounded, mechanical rules, and every caller gets the same ones. No Writ budget, payment, or label is consulted. A reviewer could still call "keep 64 KiB back" or "spend own quota on an upgrade" a resource policy. If you do, note that it is host resource policy, decided at compile time. Also note the documented exception: under a parent that answers an upgrade with PENDING, the upgrade could block (171-173).

Confirm by reading:

  1. _populate refuses with a named reason, before allocating, when the PD's available RAM is below the chunk plus RAM_MARGIN or caps are below CAP_MARGIN writ_mem.cc:648-652; it never calls the parent or Env::pd().
  2. If any piece fails to attach, _populate detaches the pieces, frees the RAM, and clears the chunk entry writ_mem.cc:665-669; no half-populated chunk remains.
  3. _upgrade_rm_session writ_mem.cc:575-594 acts only on OUT_OF_RAM/OUT_OF_CAPS, only if the PD keeps its margins after the transfer, with the fixed amounts at 570-571, and _attach_pieces stops after RM_UPGRADE_ATTEMPTS tries per piece (620); every upgrade sent or declined is counted.
  4. Pieces never cover a guard range and are mapped non-executable and writeable: for_each_piece writ_mem.cc:414-432 and _piece_attr writ_mem.cc:547-551.
