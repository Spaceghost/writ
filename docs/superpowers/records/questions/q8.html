Shim review 2 of 9: the three libc replacements (mmap, munmap, mprotect)

These are the public POSIX entry points the Bend runtime calls. The program binary's definitions shadow libc's by ordinary symbol interposition (INVENTORY.md:50-55, "How the entry points win"). The shim takes over only one shape of request: an anonymous, private, read-write mapping of at least 1 GiB. That is how the Bend runtime reserves its 8 GiB term heap and its 2 GiB per-lane stacks. Everything else goes to libc unchanged. The question for this page: does any refusal here depend on who is asking or what the memory is for, or only on whether the shim can carry the request out exactly? The inventory's "Exported symbols" table (INVENTORY.md:73-88) states the behaviour you are checking.

Claim 1

_qualifies tests only the request's shape (length, prot, flags, fd, offset); a non-qualifying call is forwarded unchanged to libc.

907	static bool _qualifies(size_t len, int prot, int flags, int fd, ::off_t offset)
908	{
909	    return len >= MIN_QUALIFYING
910	        && prot == (PROT_READ | PROT_WRITE)
911	        && (flags & MAP_ANON) && (flags & MAP_PRIVATE)
912	        && !(flags & (MAP_FIXED | MAP_SHARED))
913	        && fd == -1 && offset == 0;
914	}
1041	extern "C" void *mmap(void *addr, ::size_t len, int prot, int flags,
1042	                      int fd, ::off_t offset)
1043	{
1044	    if (!_env || !_libc_mmap) { errno = ENOSYS; return MAP_FAILED; }  /* before construct */
1045	
1046	    if (!_qualifies(len, prot, flags, fd, offset))
1047	        return _libc_mmap(addr, len, prot, flags, fd, offset);
1048

1050	    return _reserve(addr, len);
1051	}

What I see. The predicate reads its five arguments and nothing else: no caller identity, label, or Bend state is available to it. A non-qualifying call reaches _libc_mmap with the same arguments (1047). The 1 GiB threshold is a fixed shape test that separates the runtime's heap and stack reservations from ordinary allocations.

Recommendation: Confirmed, the filter reads only its arguments.

Claim 2

munmap releases only a whole reservation: an overlapping range that is not exactly the reservation is EINVAL, and a range overlapping no reservation goes to libc.

1053	extern "C" int munmap(void *addr, ::size_t len)
1054	{
1055	    if (!_env || !_libc_munmap) { errno = ENOSYS; return -1; }  /* before construct */
1056	
1057	    addr_t const a = addr_t(addr);
1058	    {
1059	        Mutex::Guard guard(_mutex());
1060	        for (Reservation &r : _res) {
1061	            if (!r.used || !_overlaps(a, len, r.base, r.size)) continue;
1062	            /* only the whole reservation can be unmapped */
1063	            if (a != r.base || len == 0 || len > r.size
1064	             || _page_round(len) != r.size) {
1065	                errno = EINVAL; return -1; }
1066	            _release(r);
1067	            return 0;
1068	        }
1069	    }
1070	    return _libc_munmap(addr, len);
1071	}

What I see. The loop finds the first reservation the range overlaps; anything other than its exact base and page-rounded size is EINVAL. The refusal is "cannot do a partial unmap", since the shim has no way to split a region map, not a judgement about the caller.

Recommendation: Confirmed, the whole-reservation rule and the libc fallthrough are both visible.

Claim 3

mprotect on a reservation either records a PROT_NONE guard or fails (EINVAL, ENOTSUP, ENOMEM); the one silent success is read-write on a range with no guard.

What I see. Validation comes before any arithmetic that could wrap. Read-write returns 0 only when no guard overlaps (1105-1110), because a reservation is already read-write; lifting a guard and any other protection are ENOTSUP, and a fifth guard is ENOMEM (the fixed table of 4). These are "cannot do this exactly" refusals, the same for every caller.

Recommendation: Confirmed, every branch either acts as asked or fails.

Claim 4

If re-attaching the pieces around a new guard fails, the guard stays recorded and the call returns ENOMEM; the shim never drops the guard to save the data.

What I see. The guard was already added at 1121 and is not removed on the failure path. The trade-off is fail-closed: data outside the guard may become unreachable, but the guard range never carries a mapping. That is a fixed safety rule, not a choice made per request.

Recommendation: Confirmed, the failure path keeps the guard.
