Unikraft lanes lane, Task 1 (change task 2.4, UL-005): a second runtime lane on a
two-vCPU Unikraft image, chased with the hello and Lanes probes.
Recorded 2026-11-05 (UTC) on Linux x86_64 (Manjaro, kernel 7.2.9), no root.

Every run below is an EMULATED BOOT under QEMU 11.1.2 with TCG (-accel tcg), machine pc,
-cpu max, -no-reboot, the isa-debug-exit device at 0xf4, -m 1024, through
hosts/unikraft/scripts/run.sh unless stated; -smp and "+RTS --threads N --gpu off" as
stated. Every run is TCG on the CPU: not native, not an accelerated boot, and no GPU was
used or tested. With -smp 2 QEMU's TCG emulates two vCPUs; nothing here measures host
parallelism. Unikraft 0.21.0 (7351f8b), kraft 0.12.16, Bend 2.0.39 (pins:
verification/unikernel-pins.txt). W = realpath ../writ-unikernel from the repository
root; nothing built is in the tree. The host was loaded (load average 26 to 76); wall
times are indicative only.

== Result ==

1. The second lane runs, but only on the boot vCPU. With "+RTS --threads 2" the runtime
   reports "lanes 2", calls pthread_create(pool_work, 1), and pool_work is entered and
   calls pool_rows on its own lane stack (0x10800ad000; the main lane's is
   0x1000069000). This differs from E6 (matrix, earlier image without the signal
   library and the exit hook), where pool_work was not entered before shutdown. In
   the observed order the second lane's pool_rows runs after both of the main lane's
   pool_turn calls; whether it claimed a row was not shown.
2. The second vCPU is never used. With -smp 2, gdb lists CPU#1 as "halted" at
   0x00000000000fd5fd (firmware range) at pool_open, at pool_work and at the crash;
   every breakpoint hit is on CPU#0, and uk_lcpu_start (lib/uklcpu/lcpu.c:297) is not
   hit. In the 0.21.0 sources uk_lcpu_start has no caller (only its definition and the
   declaration at lib/uklcpu/include/uk/lcpu/pm.h:118); plat/kvm/x86/setup.c:149-154
   calls only uk_lcpu_mp_init under CONFIG_HAVE_SMP. ukschedcoop is one cooperative
   run queue. So two lanes ran, interleaved cooperatively on one vCPU; two lanes on two
   vCPUs did not happen.
3. Every "--threads 2" Lanes run ends in a Unikraft crash after complete program output:
   "lanes 2", "pow2 4194304" (correct, 2^22), then
   "CRIT: [libukalloc] <alloc.c @  198> Assertion failure: metadata->base != ((void *) 0)"
   and QEMU 253 (the exit hook's crash value), on -smp 1 and on -smp 2 alike. gdb places
   it in the idle thread's garbage collection of the exited thread named "main":
   _uk_printk <- uk_free_ifpages (lib/ukalloc/alloc.c:198) <- uk_thread_release
   (lib/uksched/thread.c:1023, uk_thread_uktcb_fini) <- uk_sched_thread_gc
   (lib/uksched/sched.c:282) <- idle_thread_fn (lib/ukschedcoop/schedcoop.c:199).
   "--threads 1" runs of the same image end with QEMU 33. Not patched (plan: a crash is
   recorded, not patched). Whether the same crash happens with the shipped
   UKPLAT_CPU_MAXCOUNT=1 template (signals on) was not tried: no Lanes image of that
   template exists and the time box allows no third probe build.
4. hello (no parallel call, no pool) prints "hi" and ends with QEMU 33 in all four
   configurations.
