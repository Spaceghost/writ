# Proposed no-data initialization contrasts

Status: design for review only. No comparison in this document has been implemented or run. The existing strict Windows canary gate and worker profiles remain unchanged.

In [run 42313767360](run-42313767360/README.md), an independent report-only LPAC with zero capabilities and Win32k calls disabled returned Winsock `10107`, USER32 load error `1114`, and OLE32 load error `1359`, while ordinary no-data controls initialized all three successfully. This happened without a Writ mount, session or fixture bytes. The LPAC's executable, package, lifetime and inherited handles differ from the real byte worker, and the controls were not varied. We cannot infer the error mechanism, prove identical conditions, or credit confinement. This plan seeks diagnostic contrasts, not a substitute for an actual byte-worker test.

## Isolation and fixed setup

Use one fresh, disposable GitHub-hosted Windows VM for each complete trial, with no Writ service, policy, mount, canary or protected worker. The controlled-launch design must accept no arbitrary input path, payload or external destination and must provide its child exactly one report-only anonymous pipe, no standard I/O or other inherited handles, and no session, filesystem object, listener, socket, or policy pipe. Independent verification of the complete inherited-handle set remains an explicit gap below. The report carries only bounded versioned numeric facts. A direct child invocation is not the controlled launch. Never compare outputs from an admitted worker or use a comparison process as a Writ actor. The supervisor and child images and the source commit are hash-pinned and recorded; the child PE must have no direct USER32/OLE32 imports. Abort an observation when either target is already loaded before its relevant call or the fixed report is missing, malformed, late or inconsistent.

A trial uses one freshly created, supervisor-owned diagnostic AppContainer profile/package SID for all its sequential test processes and the same fixed child image and environment. This permits within-trial comparisons; the fresh SID is not the byte worker's identity. No processes overlap. Each process has its own retained PID/creation time and job; never infer identity from sharing a package, token or image. Use the existing launch behavior as the reference for reduced primary token, LPAC opt-out, exact-package AccessCheck controls, low integrity, disabled elevation, child-process policy, 64 MiB limit, one-process job, die-on-unhandled-exception, kill-on-close, job UI limits, process-object ACL and explicit handle list. Preserve the DLL loading order and Winsock startup/cleanup semantics used in the recorded first slice.

The current shared launcher hard-codes a fresh profile and one profile configuration per worker. A future diagnostic implementation must add or factor narrowly scoped test-only launch machinery to make sequential same-package comparisons possible; it must not change the existing byte worker, weaken its checks, or provide any route to canary bytes. If those controls cannot be created or read back without changing their meaning, abort the trial and record the specific unavailable fact rather than claim a match.

## Single-factor contrasts

Use the following capabilities and process-mitigation combinations, all on otherwise equivalent no-data LPAC processes with the same package-scoped WFP blocks installed and verified:

| ID | Capability SIDs | Win32k system calls |
| --- | --- | --- |
| A | none | disabled |
| B | only enabled `registryRead` | disabled |
| C | none | enabled |
| D | only enabled `registryRead` | enabled |

A versus B and C versus D differ in the one verified configured capability factor; A versus C and B versus D differ in the one verified configured mitigation factor, under the stated readback assumptions. Sharing a package can itself change per-package caches, registry or transient OS state between processes, and unmeasured OS/provider background activity can also confound comparisons. Counterbalancing and repeats can reveal some ordering or drift effects, but cannot rule these out. The diagnostic variants are never allowed data even when their capabilities or system calls are broader. Record raw Winsock and individual loader results, stage and module snapshots. Execute each configuration at least twice in counterbalanced order, e.g. A B D C / C D B A, with fresh ordinary no-data positive controls before and after. Repeat an identical baseline as needed to detect ordering and runner drift. If a control, profile check, process cleanup or module-state requirement fails, report the affected observation and comparison as incomplete; do not substitute a weaker profile. An LPAC initialization error is an observation, not a successful deny.

As a separate contrast, keep the A configuration fixed and compare the owned WFP-on state with an owned WFP-off state, each repeated in alternating order and with no other process alive. Install/read back the four package-scoped IPv4/IPv6 connect and receive/accept blocks in a dynamic session; to switch off, close only that owned session and verify through a separate engine that its four recorded filter IDs no longer exist. Recreate and read back fresh owned blocks before switching on again. If filter control or absence cannot be established, stop. No global firewall, unrelated filter or system registry changes are permitted. WFP on/off here is a test of initialization behavior under differing controls, not an egress test; the diagnostic code makes no socket or traffic probe. It does not independently establish the absence of all system or provider traffic. The recorded first slice already reproduced errors with WFP on, and the historical byte worker also observed 10107 after its own filter removal; neither fact alone isolates a mechanism.

## Readbacks and comparison validity

Before resuming each child, fail closed unless actual readback verifies:

- Correct source/binary hashes, package SID and LPAC opt-out semantics via the same access checks; same user SID and authentication/logon LUID, no elevation and low-integrity label; distinct PID plus creation time and a retained live process handle.
- Token capability list exactly the intended zero or one enabled `registryRead` SID, independently derived and checked. Read bounded `TokenGroups`, restricted SIDs and privileges and compare canonical SID/attribute and LUID/attribute sets among variants; compare the authentication LUID rather than expecting per-process token IDs to match. Treat automatic or unexpected token differences as a failed contrast, not as silently equivalent.
- Read back all applicable configured job limit flags and values, UI restrictions, membership, child-process restriction and Win32k mitigation, comparing configured values except the one intended mitigation field. Record volatile job usage and peak counters separately; do not require the whole returned structure to be byte-identical. Confirm the process security descriptor and record the explicit handle-list attribute and stripped environment supplied by the trusted launcher. Those inputs are not independent readbacks of the child. The current launcher has no supported, independently validated before-resume enumeration of the child's complete inherited-handle set and environment. No API, bounded decoding or process-access/lifetime binding for such enumeration has yet been selected; a future implementation must identify and validate a suitable method or leave those facts unverified and the pair inconclusive. Child self-report after resume is a separate, weaker observation. If any required fact cannot be independently observed, name it as unknown and do not present that pair as a one-factor comparison.
- Read back the four owned WFP block IDs, package conditions and layers in on phases, or absence of those IDs in off phases; confirm the package and readback belong to this trial. Fresh numeric handle values, PIDs, token IDs and creation times will differ and are not assumed equal or used as authority.

Record the Windows build/image, compiler and child/supervisor hashes, exact variant/ordering, token/readback summaries, module state, raw API codes, per-process retirement and filter/profile cleanup. Bound every list and report; oversize, partial readback, failed handle closure or inconsistent metadata invalidates that trial. Sensitive or unrelated machine data, crash dumps and registry contents must not be captured. No extra capability or mitigation relaxation is applied to the byte worker.

## Controls, cleanup and interpretation

Extend the portable synthetic suite to reject unknown variant fields, unintended capability/group/privilege differences, incorrect Win32k or job values, missing/extra inherited handles, preloaded DLLs, malformed/truncated reports, failed readbacks, timeouts, process-retirement failure and WFP/profile cleanup failure. These are test fixtures for classification and control flow, not evidence that Windows enforces a restriction. On native Windows, require ordinary initialization controls, each intended profile readback, report completeness and actual owned-resource teardown; capture child PE dependencies and before-call module snapshots. Run only after independent source review on a disposable runner.

Retire the child and job before touching owned filters; verify each owned filter ID is gone via an independent engine, close/check all owned handles, and delete only the trial's private image directory and AppContainer profile. Preserve errors and failed teardown; if shared setup code has already erased resource identity, mark cleanup unverified and rely on destruction of the disposable VM as containment, not as proof of successful scoped cleanup. Do not start a further case after an incomplete cleanup.

A repeatable neighbor difference would support investigating that controlled factor under this test profile; it does not prove why Windows failed or establish any live worker's confinement. If any required field cannot be controlled or read back, label the apparent contrast inconclusive. A process with no protected or public canary bytes cannot satisfy the real worker's negative egress tests. Preserve both previous failed strict evidence and the first successful no-data observation, and keep native host qualification and the real strict gate unchanged.
