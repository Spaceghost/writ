# Bend runtime host profile design

## Context

A one-line `IO.print` program compiled with Bend 2.0.39 emits 3,074 lines of C.
Its host surface is in [docs/BEND-RUNTIME.md](../../../docs/BEND-RUNTIME.md):
anonymous memory reservation, a guard page, an alternate signal stack with
`SIGSEGV`/`SIGBUS` handlers, pthreads for lanes and IO helpers, a monotonic
clock, a self-pipe with `select`, `getenv`, `exit`, and CPU-count probes. Effect
implementations are linked per program through constructor-registered table
rows; an unregistered effect fails with "an alien request".

The gap: Writ has no definition of which of these a monitor may depend on, and
no check that a produced binary stays inside that set. The Genode, Windows,
Drift kernel, and unikernel changes each need such a definition before their
runtime tasks can be judged complete.

## Decisions

### The inventory is per Bend version and generated from the compiler

The inventory is produced by emitting C for a reference program with the pinned
compiler and recording the host calls it contains. It is tied to the compiler
version. Migrating Bend re-runs the inventory; a host qualified against one
version is not qualified for another until the diff is reviewed.

### One monitor profile, stated as allowlists

The monitor profile lists the host symbols a Writ monitor binary may import and
the effect constructors it may link. The initial allowlist is the memory, fault,
thread, clock, event-loop, process, and atomics groups from the inspection, plus
the effects `IO.print`, `IO.print_err`, `IO.now`, `IO.sleep`, exit, and whichever
authenticated channel effect a host adapter adds under its own change. Sockets,
file open/read/write, process spawning, audio, windowing, and GPU program loading
are denied for the monitor. A worker domain is not a monitor and is governed by
the confined-transformation change, not this profile.

### Verification is a build artifact check plus a corpus run

Two checks. First, a script reads the produced binary's undefined symbols (for a
dynamic build) or its linked effect table (for a static one) and fails on any
symbol or effect outside the profile. Second, the full `Tests.bend` corpus and the
four examples run on the target through the profile and must print the recorded
outcomes. The first catches accidental widening; the second catches a host whose
primitive has the right name and the wrong semantics.

### Thread count is a host parameter with a parity requirement

The runtime accepts one to 128 lanes. A host may fix the lane count, including
one. Policy decisions must not depend on the count: the corpus result under
`--threads 1` must equal the recorded four-thread result. The parallel producers
are checked against the independent verifier either way, so a lane-count change
cannot alter an authorization outcome without being caught.

### Faults fail stop

The runtime's handlers print a message and exit. A host that cannot deliver a
fault to the handler, or that resumes execution after one, is outside the
profile. On a freestanding host the equivalent is a trap that halts. There is no
profile in which a memory fault inside the monitor continues.

### CPU fallback stays labeled

`--gpu off`, a machine without a device, or a host without device support all
run `!` calls on the CPU pool. The profile records this as the executed mode.
Nothing in this change creates GPU evidence; that remains with
[validate-physical-gpu-execution](../validate-physical-gpu-execution/proposal.md).

## Failure and denial behavior

A binary outside the profile fails the build check; the host is not qualified.
A corpus run with any differing line fails qualification for that host. An
alien effect request at runtime terminates the program, which is the existing
runtime behavior and is kept rather than softened. Missing host primitives deny
startup; the runtime already exits on a failed reservation or thread creation,
and the profile requires that behavior to be preserved on every host.

## Evidence before claiming implementation

- The inspection document for the pinned Bend version, regenerated by command.
- The profile allowlists checked into the repository.
- The check script, with a deliberately widened binary shown to fail it.
- Corpus and example output captured per host target, with lane count and GPU
  mode recorded, kept in `verification/` beside the existing records.
