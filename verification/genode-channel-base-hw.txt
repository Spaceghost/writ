    bad_length the component lines of monitor and clients (excluding the

    both kernels; substitute, claim_ignored, and routed_s are also in the

    shim; both run scripts were changed to accept the base-hw behaviour,
    with the reason (DIFFERENCES). No shim change was needed for them.
  - Wake path observed (WAKE PATH): Genode.take runs on the runtime's
    io_help thread 'pthread.0', not on the main thread, and parks in the
    shim's semaphore when no entry is queued; the client's signal (handled
    on the "writ_channel" entrypoint) ups the semaphore and the take
    returns; the loop then logs the decision. Same thread and same
    behaviour on base-linux.
  - check-binary.sh on the base-hw monitor ELF: rc 1, effect rows exactly
    Genode.log Genode.put Genode.take (outside the monitor profile, the
    host channel effects); the symbol half fails against the Linux allow
    list, as on base-linux. The allow lists were not edited.
  - No GPU-shaped path ran on a device: the monitor has no `!` call
    (BANGS 0); the two programs with `!` calls (Tests.bend BANGS 1,
    GpuExample.bend BANGS 3) ran on base-hw with --gpu off, so the
    runtime's `gpu != 0 && BANGS != 0` test is false and the CPU path ran.
  - OpenSpec 1.16.0 strict validation passes (OPENSPEC).

DIFFERENCES FROM BASE-LINUX (host behaviour, not the shim)
  1. liveness, after the monitor's exit. base-linux: writ_client_s signals
     again and then blocks in lx_sendmsg (connection refused). base-hw:
     the monitor's exit destroys its RAM dataspaces, which are the
     client's buckets, so they vanish from S's address space; S's next
     record write faults and core logs
       Error: illegal WRITE at address 0x4010 by pager_object: pd='init -> writ_client_s' thread='ep' ip=0x100b8d1
     addr2line -f -C -e ../writ-genode/build/x86_64-hw/app/writ_channel_client/writ_channel_client.debug 0x100b8d1
       Writ_channel_client::Main::_write(unsigned int, unsigned int)
       .../writ_channel_client.cc:277   (_request[HEADER_WORDS + i] = record[i])
     i.e. the first record word at bucket offset 0x10 (bucket at 0x4000).
     The run script ended at "flood request N signalled" after the
     monitor's exit; on base-hw it now ends at that core line after the
     monitor's exit (writ_bend_monitor.tcl, writ_bend_monitor_liveness_run).
     Every monitor-side requirement is unchanged. First base-hw run with
     the old condition: rc 2, timeout after the core line
     (../writ-genode/run-hw-writ_bend_monitor_liveness-t3b.out).
  2. dead_client, the freed result context. base-linux: core's signal
     proxy warns "invalid signal-context capability"
     (repos/base/src/core/include/signal_delivery_proxy.h:70). base-hw:
     Signal_transmitter::submit is a kernel call, and the kernel ignores a
     signal to an invalid capability without a message
     (repos/base-hw/src/core/kernel/thread.cc:395-400,
     "/* ignore invalid signal */"). The warning is required on base-linux
     only; on base-hw the freed-context client's own decision before R's
     decision and the monitor's continued service remain required. First
     base-hw run: rc 1, "missing core warning for the freed context"
     (../writ-genode/run-hw-writ_bend_monitor_dead_client-t3b.out).
  Both changed scenarios were rerun on both kernels (t3c), and then all
  eight on both kernels with the final tcl (t3d), rc 0.

WAKE PATH (observed on both kernels, every run)
  Instrument (shim channel section, diagnostics only): before each down
  of _channel_ready, take notes whether the semaphore was empty (the down
  parks the thread; counted as "take parked" in the exit report), and the
  first take logs the thread it runs on. Observed lines:
    accept (base-hw):  writ_channel: take runs on thread 'pthread.0', parks in the semaphore
    substitute (hw):   writ_channel: take runs on thread 'pthread.0', semaphore already up
  The base-linux runs log the same thread name. In accept the order on
  base-hw is
    [init -> writ_client_r] client: waiting 2000 ms before writing
    [init -> writ_bend_monitor] monitor: serving 8 records
    [init -> writ_bend_monitor] writ_channel: take runs on thread 'pthread.0', parks in the semaphore
    [init -> writ_client_r] client: request written (length 64 seq 1), signalling the monitor
    [init -> writ_bend_monitor] monitor: channel=1 ... decision=Committed ...
  so the take was parked in the semaphore before the client signalled,
  and the decision followed the signal. In liveness every one of the 7
  takes parked (take parked=7). What wakes it, observed: the client's
  signal reaches the monitor's "writ_channel" entrypoint, whose handler
  ups the semaphore; the parked thread returns from writ_shim_take. That
  thread is 'pthread.0', the first pthread the component created, not the
  main thread; writ_shim_take is called only from genode_take_call, which
  the runtime runs as an io_work job on an io_help thread
  (monitor.c:70139-70151, 70524-70527). Read in the generated C, not
  instrumented: io_help then writes the job pointer to io_wake_fd[1]
  (monitor.c:70149), and the loop's select over io_wake_fd[0]
  (monitor.c:70199-70207, through libc and the vfs_pipe /pipe mount)
  returns and packs the Request (io_take). This is the same mechanism as
  on base-linux: the helper's semaphore, then the runtime's own pipe. No
  base-hw-specific wake path, spin, or polling was needed; the shim's
  channel section was not changed for base-hw.

LIMITS
  Emulated boot only. One lane. The channel's authority state is
  synthetic. The wake path's last hop (io_wake_fd through vfs_pipe to the
  loop's select) is read from the generated C, not instrumented; the
  instrumented part is the take's thread, its park, and the log order.
  Nothing restarts the monitor after fuel exhaustion (GB-008's supervisor
  restart is not shown on either kernel).
