# Research only: next path for the strict Windows worker

The real byte worker in [run 42311207831](../../../../contrib/native-hosts/windows/verification/run-42311207831/README.md) read and revoked the public canary, but its network, clipboard and COM checks did not reach the required explicit-denial outcomes. The combined [no-data run](../../../../verification/windows-combined-ad-observation-42323792791/README.md) observed successful initialization in different child lifetimes when two controls differed; it does not repair or qualify that worker. No supported, restriction-preserving fix is established by the evidence so far.

## What the current evidence and APIs say

In `probe.c`, one `WSAStartup` error is copied into the four network result fields; it is not four observed socket denials. The strict worker saw 10107 with and without its owned WFP filters. Microsoft says [WSAStartup returns its own error and must succeed before later Winsock calls](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-wsastartup); [10107 is generic WSASYSCALLFAILURE](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2), with multiple possible sources. It does not prove registry denial or network restriction. A socket test that cannot initialize must continue to fail or remain incomplete.

`channels.c` reports USER32/OLE32 stage-1 library-load failures before the intended clipboard and COM operations. [LoadLibraryExW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw) can fail due to a target or dependency; these errors do not identify which component failed. Microsoft describes [Win32k disable](https://learn.microsoft.com/en-us/windows/security/book/application-security-application-isolation) separately from the more detailed [mitigation compatibility explanation](https://learn.microsoft.com/en-us/defender-endpoint/exploit-protection-reference#disable-win32k-system-calls); it is intended for non-UI processes, but that does not prove the specific loader-failure mechanism or cover every potential clipboard/COM path. Readback of that mitigation is useful configuration evidence, not a substitute for an observed forbidden-effect test.

Microsoft's [LPAC description](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) documents that registryRead and lpacCom grant access relevant to restricted resources; the no-data correlations do not show why 10107 occurred or whether a narrower configuration would suffice. Microsoft describes [WFP and filter arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/about-windows-filtering-platform) and [ALE per-connection/socket classification](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-). Reading back a package filter establishes its configuration, not that the particular real worker's attempted traffic was blocked, nor equivalent protection after that filter is removed.

The held source, runner and PE/import captures from the [registryRead](../../../../verification/windows-registry-ab-observation-42322440747/README.md), [Win32k](../../../../verification/windows-win32k-ac-observation-42323201217/README.md), and combined no-data runs provide a bounded build comparison, but the real probe image has a different command, handle list and lifetime. No specific build defect or invalid API call has been established; successful initialization in another image is not evidence that the strict worker could issue its blocked-effect tests.

## Smallest useful next preparation

First do a **design and source-only** feasibility review for a bounded pre-admission initialization phase in the *same creation-returned strict worker process* that could later receive the public canary. The current `writfs.c` admits and resumes the worker, and `probe.c` reads the canary before its initialization probes; a pre-admission phase therefore requires an explicit protocol/order change, not merely a new diagnostic flag. A candidate would retain the worker PID, creation time, held image, zero-capability LPAC token, Win32k disable, original child/job/UI controls and owned WFP readbacks across both phases. It would run only bounded fixed initializers and emit stage/status/module-timing data before admission, with no fixture bytes, mount handle, policy pipe, supplied protected path or caller-selected probe. No diagnostic phase may grant policy authority or provide a release path. The broker must keep the actor unadmitted until an independently reviewed transition, and a failed or missing control remains incomplete. Verify lifecycle binding and bounded report framing, no pre-admission data route, owned cleanup on all failures and a positive ordinary control. Initializers, reports and the handoff can leave handles or mutable OS-visible state in the same process: before admission close those channels and verify they are absent, or explicitly mediate and scope them under the existing information-flow and commit rules. At the transition revalidate the actual worker lifetime, token, job, mitigation, reachable handles, monitor/session and authority with no race or unapproved peer; PID and package SID alone are insufficient. Record pre-admission state contamination and initialization perturbation rather than assuming the same process is clean. Do not assert environmental or token facts not independently verified.

This would improve attribution to the same worker lifetime if safely implemented, but it would **not by itself make the strict network/clipboard/COM checks pass** or prove any native confinement. If initializing before admission changes libraries, handles, timing, or later behavior, record that perturbation; compare to the original order and do not silently change the acceptance test. The existing worker's public-canary command currently includes mount path and digest, and it has three inherited synchronization/report handles, so the proposed no-data phase is not already present. Establishing a safe, authenticated later handoff and preserving identical policy/actor identity require a separate source/spec/security review. If the contract cannot be maintained, do not implement it.

As a supplementary *separate no-data diagnostic only*, a fixed-key, open-only registry observation could distinguish the specific key/view's accessibility under zero-capability LPAC and ordinary controls. [RegOpenKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw) returns an explicit status, but a guessed key or view is not proof of what Winsock actually accessed. Do not enumerate or read registry values, mutate ACLs/catalogs, infer an undocumented Windows path, or use a successful separate child as byte-worker evidence. A narrowly scoped OS tracing option should be considered only after its documented provider/schema, process-lifetime attribution, privileges, resource limits and no-data filtering are independently specified; absent that, leave it unimplemented.

## Decisions and gates

Granting registryRead or another capability to the real worker, enabling Win32k, changing access-control lists, replacing the real worker with a relaxed helper, weakening network/clipboard/COM acceptance, or substituting filter readback for a failed effect probe changes the security design or evidentiary contract. Such options require an explicit security-design decision and their own threat and acceptance review; the present evidence does not authorize them. Undocumented internal calls, bypassing WSAStartup, injecting code, modifying system catalogs or treating generic initialization failures as access denials are not supported fixes.

Keep the failed run and all diagnostic results. Under [NM008](../../../../openspec/specs/native-host-canary-mounts/spec.md), confinement evidence names the actual worker, functioning positive controls, observed native denials and gaps; the [proposed Windows contract](../../../../openspec/changes/add-windows-host/specs/windows-host/spec.md) requires verified actual-worker restrictions and no weaker fallback. Any future change needs the same actor/lifetime and a full real-worker acceptance run; no source change or native execution is authorized by this research note.
