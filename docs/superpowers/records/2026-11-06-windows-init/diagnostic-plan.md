# Windows LPAC initialization: no-data diagnostic plan

Status: original design plan. The first standalone initialization observation has since been authored but has not been built or run on Windows. Its separate executable, package and report-only handle list differ from the byte worker; final-token group/privilege equivalence and the proposed factorial matrix remain unimplemented. No result changes admission, native confinement, or acceptance criteria.

## Observation and boundaries

The strict byte-worker test at source `9c08eb93b86a6025d3b254551557e394f7685f7c` failed in [Windows native run 42311207831](https://github.com/Spaceghost/writ/actions/runs/42311207831). The byte worker reports `e7..e10=10107`, `clipboard_stage=1` / `0x8007045a`, and `com_stage=1` / `0x8007054f`; it reports network, clipboard and COM confinement incomplete. The same worker again reported 10107 after the owned WFP blocks were removed. The test's mount, reader, wrong-process denial and revocation checks passed, but the strict overall job failed. A [prior run](https://github.com/Spaceghost/writ/actions/runs/41778041710) exhibited the same initialization errors; that is recurrence, not a cause.

`contrib/native-hosts/windows/probe.c:101` invokes `WSAStartup` once; its error is copied into four network fields, so these are not four independent socket failures. Microsoft documents that [WSAStartup returns its own error code](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-wsastartup); [10107 is WSASYSCALLFAILURE](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2), a generic system-call failure with multiple possible sources. `channels.c:11` and `:35` report failures while loading `user32.dll` and `ole32.dll` before the clipboard/COM access checks. These HRESULTs wrap Win32 [1114, ERROR_DLL_INIT_FAILED](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1000-1299-) and [1359, ERROR_INTERNAL_ERROR](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1300-1699-). [LoadLibraryExW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw) can load dependencies: the observed error does not identify the failing module or mechanism. None of these codes establishes a registry, Win32k, WFP, host-image, or product-code root cause.

The existing no-data diagnostic (`worker.c:524`) is a different process and lifetime with the worker's package SID, `registryRead` capability, and Win32k calls enabled. It also has a different job limit set: a process-time limit rather than the byte worker's die-on-unhandled-exception limit (`worker.c:370`, `:559`). It uses only a report handle and public loopback ports, and returns stage-3 denials in the recorded run; it cannot identify which of its differences matters or establish the real byte worker's restrictions. Its success does not change the failed strict result. See `writfs.c:777` for the incomplete gate and `:798` for the two WFP phases.

## Proposed experiment

1. Use a disposable isolated Windows environment and a dedicated, synthetic no-data fixture, with no mounted volume, protected bytes, canary file/path, Writ filesystem handle, private policy pipe, broker admission, actor identity, or protected worker running. Pass only a bounded report handle and, only for optional network checks, numeric ports for dedicated public loopback receivers. Deny unintended handle inheritance and ensure standard handles are absent. Run no probe until this isolation and cleanup can be verified.
2. First reproduce the byte worker's creation controls in a **separate** no-data process: LPAC opt-out; same reduced user/logon and package SID for a given experiment; low integrity; zero capability SIDs; same token groups/privileges and access checks; child creation restricted; same job active-process, memory, die-on-unhandled-exception and UI restrictions; Win32k system calls disabled; equivalent environment, executable image and launch attributes. The report-only handle list necessarily differs from the actual worker's three private handles, and the command/mode is diagnostic; record these differences explicitly. Compare only verified properties and do not call this a clone of the live worker or the same identity. A [mitigation readback](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessmitigationpolicy) and token/job readbacks must confirm the intended variant before executing it. Record PID, creation time, source and executable hashes and reject failed or ambiguous readback.
3. Under the same disposable setup, use a 2 x 2 diagnostic matrix: zero capabilities versus only `registryRead`, crossed with Win32k system-call disable on versus off. Keep all other **verifiable** controls fixed, including job limits and image; label the relaxed variants no-data diagnostics. Compare single-factor neighbors, not only the opposite corners. Windows documents the [Win32k system-call mitigation](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-process_mitigation_system_call_disable_policy); its existence does not establish why a library initialization failed. If any other control differs or cannot be observed, mark the comparison inconclusive.
4. Treat WFP as a separate axis. In this isolated environment install the same kind of owned, ephemeral package-scoped four outbound blocks, verify all four, then observe on/off phases with only those owned filters removed between phases. Never remove other filters, change global firewall policy, or run the off phase while any protected-data worker exists. Record filter ownership, successful removal and cleanup; a failed cleanup invalidates the run. Repeat the baseline as needed on both sides of a phase transition to reveal ordering effects. No filter manipulation is needed to test DLL loading alone.
5. Start with initialization only: invoke `WSAStartup` once and record its direct return, calling `WSACleanup` only on success; independently call `LoadLibraryExW` with system32 search for each DLL, capture immediate `GetLastError` when it fails and unload successful handles. Record exact stage, raw code, bounded fixed-format result and exit status. No socket traffic, clipboard access, COM activation, payloads or filesystem data is needed for this first pass. If initialization succeeds and network behavior needs follow-up, use separately bounded public loopback receivers with positive controls and fixed test bytes; record traffic and phase without treating this as restriction credit for the actual worker. Any additional targeted read-only OS tracing must be scoped to the diagnostic PID, exclude payloads and paths, document perturbations, and remain diagnostic; avoid collecting dumps or unrelated process data.
6. Run same-runner ordinary no-data positive controls before and after the matrix to check that Winsock and the two loads work outside LPAC. Add synthetic report/parser tests for forced WSAStartup failure, loader failure at each stage, malformed/truncated reports, wrong profile readback, timeout and cleanup failure; each must remain unknown/incomplete and must not grant a confinement pass. Synthetic fault injection verifies classification only, not real Windows restrictions. Check the inherited handle allowlist and that no mount, Writ session, data handle or admission path is present. Retire each process and only its own job, profile, test listeners and WFP resources, verifying cleanup.

## Interpretation and evidence

Save the exact runner/OS version, build and binary hashes, profile readbacks and deviations, raw bounded reports, listener controls, phase ordering and cleanup outcomes. Preserve the original failed run and existing no-data result. A repeatable matrix difference can guide investigation but is not, by itself, proof of a causal Windows mechanism; rerun controlled changes and use official API documentation or targeted evidence before making a causal claim. If errors remain or equivalence cannot be verified, report unknown and retain incomplete status. `10107`, DLL initialization errors, a broader token or disabling Win32k must never be accepted as a confinement denial.

A diagnostic process that shares package/token properties is still a different PID and creation lifetime and must not impersonate the original process or be treated as an admitted Writ actor. Any later confinement credit requires appropriate real checks in the actual byte worker and positive controls, not these variants; host qualification remains separate and requires its full evidence. Applicable contracts: baseline `openspec/specs/native-host-canary-mounts/spec.md` NM004 and NM008 and proposed `openspec/changes/add-windows-host/specs/windows-host/spec.md` WH-001 through WH-004, WH-007 and WH-010. Bend remains authoritative for policy.
