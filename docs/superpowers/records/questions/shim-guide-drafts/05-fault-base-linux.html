Shim review 5 of 9: the fault decision and the base-linux SIGSEGV path

On base-linux, Genode components are ordinary Linux processes, and an unpopulated part of a reservation is a PROT_NONE Linux mapping. Touching it raises the Linux signal SIGSEGV. A signal handler here means a Linux one: a function the kernel runs on the faulting thread. (Genode also has its own Signal_handler, an asynchronous notification dispatched by an entrypoint. That one appears on page 6.) Genode's own region-map fault notification is never delivered on base-linux (header 76-83). So the shim installs a raw SIGSEGV handler with the rt_sigaction system call, replacing base-linux's handler for the whole process (88-89). Both platforms share one decision function, _resolve_fault (688-696). Read it first. It is the only place that chooses between "populate" and "refuse". Then read the Linux front end. The base-linux row of INVENTORY.md:274 ("Fault delivery" table) and the concurrency note at :689-705 describe it.

Excerpt, writ_mem.cc:711-745 (tabs shown as four spaces):

static void _segv_handler(int, Lx_siginfo *info, void *)
{
    /*
     * si_code <= 0: sent by kill/tgkill/sigqueue, not a memory fault.
     * Returning would not re-raise it, so take the default action now.
     */
    if (info->code <= 0) {
        raw("writ_mem: SIGSEGV not from a fault (si_code ", info->code,
            "), component terminates");
        Lx_sigaction dfl { (void (*)(int, Lx_siginfo *, void *))LX_SIG_DFL,
                           0, nullptr, 0 };
        lx_rt_sigaction(LX_SIGSEGV, &dfl);
        lx_syscall3(LX_SYS_TGKILL, lx_syscall3(LX_SYS_GETPID, 0, 0, 0),
                    lx_syscall3(LX_SYS_GETTID, 0, 0, 0), LX_SIGSEGV);
        return;
    }

    addr_t const a = addr_t(info->addr);

    Mutex::Guard guard(_mutex());

    Reservation *r = _lookup(a);
    if (!r) { _refuse("outside every reservation", a); return; }

    bool populated = false;
    if (char const *why = _resolve_fault(*r, a - r->base, populated)) {
        _refuse(why, a); return; }

    if (populated) {
        /* benign race (see header): retry, but not without bound */
        if (!_retry_allowed(a)) {
            _refuse("populated chunk, fault keeps recurring", a); return; }
        _benign_retries++;
        return;
    }

Limit or policy? MAX_RETRIES (293, used at 510-519 and 741-742) is the clearest "decides to kill" rule in the memory half. It is a bounded mechanical limit: it exists only so that a fault the shim cannot fix does not loop forever, and it reads nothing but a page address and a counter. Its stated flaws are both mechanical (494-501). A page that races harmlessly more than 16 times over a reservation's life is killed (a false positive). More than 16 stuck addresses at once can evict each other and livelock (a false negative). Neither is a Writ decision. Whether a false-positive kill is acceptable is an availability question, not a GB-006 one.

Confirm by reading:

  1. _resolve_fault writ_mem.cc:688-696 has exactly four outcomes (outside, guard, already populated, populated now or refused by _populate) and reads only the reservation's size, guard list, and chunk table.
  2. A SIGSEGV not generated by the kernel (si_code <= 0, from kill/tgkill) is not treated as a fault: the default action is restored and the signal re-raised on the thread writ_mem.cc:717-726.
  3. The base-linux refusal writ_mem.cc:702-709 prints one raw line, restores the default SIGSEGV action, and returns; the retried access then kills the process. Nothing on this path populates a guard or maps memory somewhere else.
  4. An already-populated chunk is retried only while _retry_allowed writ_mem.cc:510-519 allows (at most 16 per page in 16 round-robin slots), and refused after that (741-742).
