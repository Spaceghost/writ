Recorded 2026-11-04 on Linux x86_64 (Manjaro, kernel 7.2.9), no root.

== Result ==

The Bend program scripts/unikernel/Probe.bend, importing hosts/unikraft/effects/Unikraft.bend,
built as an image with the exit hook and the host layer, wrote its four "probe:" lines to the
serial console through Unikraft.log (writ_uk_log -> uk_console_out); the program makes no
IO.print call, so every line seen came through the twin. Two Unikraft.now readings around
Unikraft.sleep(100) differed by 100, 100, 100, and 101 ms (runs E2 to E5), ordered,
inside [100, 1100); QEMU 1 each, check-image.sh PASS. The FAIL branch (scratch copy requiring a
delta of at least 1000 ms) logged its FAIL line and ended with QEMU 3; check-image.sh exits 1
on it (E6). check-binary.sh sees exactly Unikraft.log, Unikraft.now, Unikraft.sleep as effect
rows, all three outside the monitor profile (E7). The first build ran the sleep on an io_work
helper thread and ended with QEMU 255 (E1); the sleep now runs on the loop thread.

Sleep mechanism: uk_sched_thread_sleep (lib/uksched/include/uk/sched.h; lib/uksched/sched.c:348)
from host.c, in a loop that re-reads ukplat_monotonic_clock until the deadline, at most 16
scheduler sleeps, exiting 1 on a frozen or backward clock. Why not nanosleep: in 0.21.0 it is
uk_sys_nanosleep, which under CONFIG_HAVE_SCHED calls the same uk_sched_thread_sleep
(lib/posix-time/time.c:69-97); calling it directly avoids the syscall shim and its EINTR
remainder. Why on the loop thread, not io_work: see E1. In these runs the loop never needed a
second scheduler sleep (each delta is the sleep or 1 ms more); the re-sleep and failure paths
of writ_uk_sleep_ms were not exercised by a fault (not forced: there is no clock fault to inject
without patching Unikraft).

  The helper thread ran (the first IO helper thread exercised on this target: the sleep
  completed and woke the loop through the runtime's wake pipe), but QEMU ended with 255,
  "status above 0x7c". Cause, read from the source, not traced: the runtime's io_help
  thread loops forever, so when main returns the init process (pid 1) still has a running
  thread; with CONFIG_LIBPOSIX_PROCESS_SIGNAL not set, lib/posix-process/shutdown.c:96-101
  then sets exit_code = 0x80 | SIGKILL (137), which exit_device.c maps to 0x7f (QEMU 255).
  WRIT_NO_BOOT=1 check-image.sh on this capture: diff empty, "QEMU exit: 255, expected 1",
  result FAIL, exit 1. Consequence: on this configuration an io_work effect makes every
  successful run end as 255. unikraft_sleep.c therefore blocks the loop thread instead;
  the cost is that no other computation of the program runs during a sleep. Task 2's
  blocking take meets the same limit.
