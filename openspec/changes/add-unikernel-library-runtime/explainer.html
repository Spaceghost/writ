Make the Bend runtime fit an existing unikernel

Change add-unikernel-library-runtime, plus the candidate survey in docs/UNIKERNELS.md. The theme is not to build a kernel. It is to pick one that already boots, link the Writ monitor into it natively, and let the image be nothing but the monitor and the kernel pieces it needs. Proposed; nothing built.

Two ways to fit a runtime into a unikernel

Binary compatibility

The unmodified Linux ELF of the monitor plus a kernel that emulates enough of the Linux syscall ABI. Nothing in the Bend build changes.

appliance change Fastest first boot. Carries an emulation layer the monitor barely uses.

Native link

The generated C of the monitor compiled against the unikernel's own libc and linked into one image. Effect twins can call kernel primitives directly.

this change The end state. The monitor is the kernel's only program.

Both routes exist in the proposals on purpose. The appliance change gets a corpus booting under a compat kernel as early as possible. This change is where the theme lands.

Design in five decisions

  • Native link, not ELF loading. The generated C is the application. A compat loader in the build configuration belongs to the appliance, not here.
  • Select by an executed matrix. One cell per row per candidate, filled by running it. Unikraft first because linuxu lets the port be debugged as a Linux process before any VM boot.
  • Effect twins bind to kernel primitives. Console, time, and the ingress channel call the kernel directly; exit and crash reporting is an inventoried termination host layer, since no Bend code runs on a crash. The twins and that boot and termination host layer are the only kernel-specific code, and each file is inventoried with its exported symbols and what it may touch.
  • Single lane first, faults halt. One lane removes the pthread rows. A page fault reaches a handler that prints the runtime's message and halts with a distinct code.
  • Three environments, recorded apart. As a Linux process, under QEMU software emulation, under Firecracker or KVM. Only the last two are boots.

Deployment rules are inherited from the appliance change unchanged: image contents, reproducible hash, single ingress, external state, clock and entropy checks, the timed rebuild drill, and the trusted-base statement. A library image is an appliance image built differently.

Milestones

  1. Pin Unikraft and OSv. Build the hello program's generated C as a native application on each. Record build outcome.
  2. Fill the matrix by executing each row on each. Publish the choice with reasons.
  3. If Unikraft: run under linuxu. Record as process execution, not a boot.
  4. Author the console, time, and ingress twins (exit is the inventoried termination host layer). Inventory them. Run the binary check on the image.
  5. Single lane. Corpus and examples under QEMU. Line-for-line match with the Linux record.
  6. Halting fault handler. Forced overflow and arena exhaustion with distinct codes.
  7. Enable lanes. Match preserved. Boot under Firecracker or KVM. Separate record.
  8. Apply the appliance rules including the rebuild drill.

Where a subagent starts

This lane needs Unikraft's kraft tooling and a QEMU, both installable without root. The subagent should begin with the hello program, not the corpus, and with linuxu, not a VM: the goal of the first day is a filled matrix, not a boot. It must keep every generated C file and image outside the source tree, and it must not patch the Bend evaluator; if a row cannot be satisfied, the answer is a substitute from the runtime profile or a recorded "missing," never a fork of the runtime.

It should read docs/BEND-RUNTIME.md, docs/UNIKERNELS.md, bend guide effects, and the appliance change before writing anything.
