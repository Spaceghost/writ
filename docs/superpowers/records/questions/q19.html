Linux host: how should we proceed with identity evidence?

Decision needed: should I test the Bend monitor with synthetic identity facts now, or leave the identity task open and move on to Linux confinement? Both can be pursued while waiting for Spaceghost's broader architecture answers.

Why identity matters

A Linux broker launches a worker and needs to know which worker is sending a request. A claimed name or possession of a socket alone must not grant someone another worker's authority. The intended host checks associate kernel-observed credentials with a trusted launch record and the worker's lifetime; the Bend monitor then makes the authorization decision.

For example, if a worker passes its socket to another process, the second process must not become the original worker merely by holding it. The host acceptance task also calls for testing claimed identities, parent-created socketpairs, process ID reuse, and namespace identity mapping.

What is done and what is missing

The Linux lane has an initial Bend adapter and a partial native broker, launch record, codec and invocation harness, saved at b47fd90. The native identity probe and its evidence were not completed. The work has not been qualified as a working Linux host; box 1.2 remains open. The prior session reported that an automatic safety classifier stopped two attempts to write the native probe.

The full acceptance contract remains in openspec/changes/add-linux-host/tasks.md, item 1.2, and the LH-002 and LH-007 scenarios in openspec/changes/add-linux-host/specs/linux-host/spec.md. The task brief and partial-work ledger are in the linux-host worktree at docs/superpowers/records/2026-11-05-linux-host/.

Options and recommendation

I recommend synthetic facts first. We can feed known mismatches such as a wrong start time or foreign session to the monitor and check that it denies them. That would exercise the Bend side only; it cannot establish that the broker obtains authentic credentials or resists transferred endpoints on Linux. The real kernel-level cases and box 1.2 stay open.

Alternatively, we can defer those tests and start the confinement task: prepare and test the controls intended to be installed before protected input reaches a worker. This work must retain the identity gap and cannot qualify the whole host by itself. You can also provide native probe case bodies for integration, subject to any applicable tool restrictions and review.
