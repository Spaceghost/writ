# Design only: combined no-data initializer observation

The [registryRead run](run-42322440747/README.md) observed Winsock status 0 with registryRead but Win32k disabled, while USER32/OLE32 remained 1114/1359. The [Win32k run](run-42323201217/README.md) observed USER32/OLE32 status 0 with Win32k enabled but zero capabilities, while Winsock remained 10107. These were separate runs and child lifetimes. A small combined observation could answer a narrower unanswered question: in the same fixed no-data child, do all three initializers report zero with both settings applied? That observation would add joint-status evidence, not prove a cause, an interaction mechanism or byte-worker confinement.

## Minimal sequence and controls

On a fresh disposable hosted Windows runner use ordinary positive controls bracketing a single shared fresh no-data package with A/D/D/A separate child lifetimes:

| Arm | Actual token capabilities | Win32k disable creation input and actual bit |
| --- | --- | --- |
| A | zero | ON / 1 |
| D | exactly one derived registryRead SID with exactly `SE_GROUP_ENABLED` | OFF / 0 |

A and D deliberately change **two** configured fields together. This is a joint-status observation, not a one-factor contrast or factorial experiment. A successful D report could show all three observed initialization statuses in one retained lifetime; it cannot attribute any difference to either field or establish independence, and a nonzero result can be affected by ordering, package state or other unknowns. A repeat of a prior isolated result is not assumed. No change to the strict byte-worker launch, its gate, Writ policy, or host qualification follows from any outcome.

Keep the exact fixed no-data child, held private-image digest, launch identity and reduced primary token, AppContainer package SID, explicit report pipe, observer and child jobs/UI limits, child-process restriction, WFP package blocks, supplied environment input, bounded PSS capture and report protocol from the reviewed [registryRead](registry-ab-implementation.md) and [Win32k](win32k-ac-implementation.md) implementations. No session, protected/public canary, data fixture, caller-supplied data/handle/path, byte worker, policy pipe or general endpoint is permitted. The Windows loader/providers may consult OS state; do not log its contents. D has no proven GUI or ambient-resource confinement; add no clipboard, screen/input, window enumeration, COM activation or socket/traffic probes. `WSAStartup` remains the fixed initializer; the child issues no explicit traffic, but that API may itself cause provider or OS activity which is not independently observed.

Before each resume, independently query the retained child's bounded actual `TokenCapabilities`: A must have count 0; D must have exactly the documented-success derived registryRead SID and exactly enabled attributes, with unknown output incomplete. Check actual LPAC AccessCheck facts as well as user/package, low integrity, non-elevation, authentication LUID, groups, restricted SIDs and privileges; compare selected canonical facts to A while validating the deliberate capability difference separately. Record counts and capability attributes without exposing raw token fields, and say that reviewers cannot independently reconstruct the selected sets. Use successful-output-only ownership, bounds and checked `LocalFree` for all derived arrays/SIDs, tokens and setup allocations; discard unspecified API-failure outputs and keep cleanup uncertain. Compare the fixed constructed environment input privately but do not claim the child's full environment is independently read.

Record and validate the **actual full creation-policy input** and `ProcessSystemCallDisablePolicy` readback on each retained child: A ON and disable bit 1; D OFF and disable bit 0. Reject reserved/unknown flags, unexpected creation bits, mismatched known non-varied flags or unsupported readback. Require the same observer-job configured limits/membership, child outside the observer job and inside its own restricted job, child mitigation/UI/job fields and four owned WFP filter IDs/layers/actions/package conditions. Preserve volatile counters separately from configured fields. Unknown or mismatched required controls stop the entire sequence as incomplete.

## Bounded output and retirement

For each suspended self-created child retain its process/thread, PID, creation time and held image; require bounded PSS before/captured/walked/after counts, exactly the known report pipe, and positive object identity comparison. Check release of the duplicate, marker and snapshot, close the parent writer, resume that original thread exactly once from previous suspend count 1, and require the same child to exit within its deadline with exactly one complete report and EOF. Record raw Winsock/USER32/OLE32 and module snapshots even if a later gate fails. `pre_ole32_modules` bit 1 is USER32 and bit 2 OLE32. The complete cold-load gate requires both modules absent initially and after Winsock, and OLE32 absent immediately before its explicit load; require checked initializer cleanup and mark unknown or failed cleanup incomplete. PSS is pre-resume only; it does not establish later handle state or absence of alternate paths.

Abort on any unsuccessful case, unsupported OS behavior, timeout, unknown setup ownership, unverified exit or cleanup. Never release shared WFP/profile controls while child exit is unverified. Normal shared cleanup must check dynamic WFP session close and use a separate owned engine to verify all four owned filter IDs absent, then check profile, private image, token, SID and handle retirement. A disposable VM is the fallback, not verified cleanup. Document void-returning cleanup APIs and untested native fault paths. Capture runner/ref/source/binary hashes, child PE dependencies, bounded stdout/stderr, supervision, exact statuses and artifact hashes, including failure; temporary exact-ref dispatch scaffolding stays off master.

Before any separately reviewed implementation or run, add synthetic positive and negative tests for A and D capability SID/attribute/readback, ON/OFF creation and actual mitigation bits including unknown bits, selected-token comparison, A/D/D/A stop sequencing, malformed/trailing reports, timeouts and cleanup uncertainty. Existing PSS/pipe tests and synthetic classifiers do not prove native error handling. One reviewed Windows run could provide an exploratory observation only; no test is authorized by this design.
