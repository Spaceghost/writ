Should the local supervisor channel use per-message kernel sender identity?

Josh, the owned-process test you approved in question 23 passed on Linux 7.2.9. When one child handed its socket end to another, the kernel's per-message sender handle (SCM_PIDFD) named the child that actually sent each message, not the original holder. A message queued just before its sender exited still named that sender, and malformed, oversized or extra control data was rejected without leaking descriptors.

The local supervisor profile still lists this mechanism as only a candidate. The next bridge step needs a decision: do we select it for the protected administrator and worker channels, so we can build the native receiver?

What selecting it would mean

We would build a small native receiver under contrib/native-hosts/linux/, using the same receive rules the test exercised. It would only translate facts. It would compare each message's sender handle against the process lifetimes the supervisor launched and retained, then hand Bend a bounded fact: "message from retained role N", "unknown sender" or "malformed". Every decision would stay in Bend, including which role may do what, the issuer, revocation and the clock. Testing would use only our own disposable processes, as in question 23.

The profile would be restricted to a 64-bit kernel with pidfs. If the kernel lacks the needed semantics, the receiver refuses to start rather than falling back to user IDs, process numbers or socket possession.

What it would not establish

A sender handle names a process lifetime, not a person, a program image or a role. A process holding CAP_SYS_ADMIN or CAP_SETUID in the relevant namespace can supply other credentials, and a process can exec a different program while keeping its lifetime. The profile therefore still needs protected role provisioning, no capabilities for untrusted senders, namespace and ptrace isolation, and a decision about exec. None of that is built yet, and choosing the transport does not qualify a host.

Alternatives: keep the transport open and continue only synthetic model work, or evaluate another mechanism first, such as one inherited socket pair per role created at launch, which avoids passing endpoints at all.
