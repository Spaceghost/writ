Do Genode's capabilities have the right shape for Writ?

Partly. They are the right shape for who can reach what. They are the wrong shape for what a Writ grant is. This page separates the two, checks the alternatives, and says what that means for the Genode lanes already proposed.

Verdict

A Writ grant is registry-shaped: bound to an authenticated subject, scoped to one exact plan (ordered inputs with versions, destination, write domain, code identity, operation kind, three epochs, exclusive expiry), paired with its counterpart grant, and re-resolved against live state at every use and again at commit. No kernel capability encodes that, and none should try. Genode's object capabilities are reachability-shaped: an unforgeable reference to an RPC object, delegable by invocation, routed and quota-bounded by a parent. That is exactly the layer Writ needs underneath its registry and exactly the layer it lacks today.

So: use Genode capabilities as unforgeable references to monitor-owned records, never as the records. Keep Genode as the reference host for confinement topology, interposition, routing identity, and quotas, where its shape is better than the alternatives. And fix one thing in the capability-adoption proposal, because Genode cannot tell the monitor who invoked an object, only which object was invoked.

The crux: Genode reports which object was invoked, not who invoked it

Parent routes a Writ session to reader Ridentity is known here, once
→
Monitor mints descriptor object D for RD now is R, as far as RPC dispatch can tell
→
R's worker passes the cap to D to component Qlegal in Genode; Q's invocations arrive as "D was invoked"
→
Monitor cannot see Qno runtime subject-mismatch denial is possible at the server

This is the one place the lane-B proposal overstated what the model can enforce. GA-005 promises that a delegated descriptor used by another domain is "denied with a subject-mismatch reason." On Genode the server never learns the holder, so that denial is a property of the model, not of the running system. The only real defense is topology: a domain holding a per-subject object must have no channel that can carry a capability out. Genode makes that topology explicit and enforceable, which is good, but it is a different claim from "the monitor denies it."

The existing Genode host spec (GN-004) and the platform doc already say this in prose: "possession of a transferable native endpoint does not automatically establish the original requesting subject; deny an ambiguous attribution." The adoption proposal needs to carry the same humility into its scenarios.

Pattern across the table: every mainstream capability system is bearer inside its trust domain. Subject binding always comes from somewhere else: a parent, a badge handed out by a trusted party, a channel topology. Writ already knew this. The question "does Genode have the right shape" therefore reduces to "does Genode give the best somewhere-else," and the answer is yes: parent routing plus explicit, quota-bounded confinement is stronger than badges alone and far stronger than per-process handles.

What this changes in the proposals

  1. Lane B, GA-005. Rewrite as two requirements. One is a model rule: a transition is denied when the alias holder differs from the binding's subject. The other is a topology obligation: a domain holding a per-subject object must have no capability-carrying channel to any domain outside its delegation record, and the host contract's confinement evidence must show it. Drop the implication that the running monitor can detect the mismatch.
  2. Lane B, add a derivation record. Borrow seL4's CDT as data: every explicit delegation is a node under the delegating alias, and revocation of an alias revokes its subtree. This is what makes PH-005's "narrow only, never widen" checkable across a chain, and it costs nothing on Genode because the model is in Bend.
  3. Lane A, the shim. Mint one channel object (request bucket, result bucket, signal) per descriptor, never share one across descriptors, and never expose an object that points at a sink. The object is the only identity the server has, so object granularity is identity granularity. Above the kernel the interaction is records in buckets, not procedure calls; Genode's RPC is only the transport.
  4. Both lanes, a non-claim. Write down that Genode caps are references to records and the records are the authority. No plan, rights, or expiry is ever encoded in a Genode object. A port that tries is wrong even if it passes the vectors.
  5. Nothing changes in the choice of reference host. On the properties where a kernel can help (non-ambient, interposition, quotas, routing identity, revoke-by-destroy), Genode is at or near the top. On the properties where no kernel helps, Writ's registry is already the right shape.

Questions for Spaceghost

  • Does the pinned Genode 26.08 still support seL4 as a base kernel? If yes, is a Genode-on-seL4 profile worth a row in the host table, for the CDT and the verified kernel?
  • Is one channel object per descriptor acceptable cost, or do you want descriptors multiplexed over one object with the monitor's registry as the only discriminator? The first gives kernel-level close; the second gives only registry-level close.
  • Should the binding model name a sensory (read-only, non-upgradable) descriptor kind explicitly, or is the rights bitmask enough?
