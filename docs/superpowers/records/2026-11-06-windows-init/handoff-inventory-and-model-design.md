# Proposed endpoint inventory and Bend model for a same-worker handoff

A broker-created one-way inbound pipe is the leading [design candidate](handoff-control-alternatives.md) for sending public test parameters after a strict worker's no-data initialization. This document specifies the **proposed** endpoint/effect inventory and a synthetic Bend-model test design. It does not add the pipe, define Windows authority in C, validate host confinement or establish that continuous reachable-resource enforcement is achievable.

## Concrete endpoint and effect inventory

`Observed` below means identified in current source, not proven complete or safe. `Proposed` entries have no implementation or Windows evidence. The broker is trusted only within its documented monitor/authority responsibilities; the worker may be hostile. Hold kernel objects and retained creation-returned process/thread handles through their stated lifetimes; PIDs, numeric handles, pipe names and random values alone are not credentials.

| Endpoint or resource | Owner, allowed direction, and authority boundary | Current fact / required evidence |
| --- | --- | --- |
| Existing worker report pipe | Worker writer → broker reader for fixed reports; broker must treat all fields, error codes, lengths and timing as untrusted output | Observed in `writfs.c`/`probe.c`; it persists across three phases. Exact framing, authorized logging and post-input information-flow mediation require a reviewed argument; worker-supplied phase/magic is not peer authentication. |
| Existing `ready` and `proceed` events | `ready`: worker signal → broker wait; `proceed`: broker signal → worker wait | Observed and inherited in the worker launch list. Signals are synchronization, not approval; establish ownership, access rights, lifetime and resistance to unintended signaling. |
| Proposed inbound handoff pipe | Broker owns writer; retained worker inherits read-only endpoint; one bounded public-fixture parameter record, never a policy grant | Not implemented. Verify each end's rights, peer/object lifetime, inherited-list scope and security descriptor, prevent unapproved acquisition/duplication, and retire both ends before protected admission or account for any survivor. Four inherited objects exceed today's hard limit of three. |
| Broker policy pipe | Broker ↔ generated Bend policy process; worker has no endpoint and no direct invocation authority | Observed as a separate process in `policy_pipe.c`; any sharing or accidental inheritance into worker must remain denied. Its existing timeout approach is not automatic proof of correctness for the new pipe. |
| Worker process, thread, token and job | Broker retains lifecycle and identity handles; worker must not acquire broker/policy process or token rights | Current `writ_worker_matches` checks retained PID/creation/liveness and request token user/authentication/LPAC facts; recheck actual object/job/token/mitigations at transition. Verify process DACLs and real denied attempts; same SID/PID or a claimed handle is insufficient. |
| WinFsp mount and file handles | Actor-bound fixture metadata/content → Bend `STAT`/`OPEN`/`READ`; denied before admission; after revoke later use denied | Current canary mount starts before `ADMIT`, and worker currently knows path at launch. NM004 permits fixed public mount structure before admission; actor-bound fixture metadata and content do not. Future preflight must not receive path/data early or obtain a data handle; mount authorization, cached opens and in-flight requests must remain scoped to actual policy decisions. |
| Public outside path and four loopback receivers | Broker creates public test controls; worker later attempts fixed forbidden effects only under strict test profile | Current positive receiver/file controls are constructed before worker creation and are synthetic, not secret exfiltration destinations. Construction and handoff after preflight are proposed future ordering; scope access, cleanup, timeout and do not grant network authority. WFP readback alone does not prove traffic denied. |
| Package profile, registry, filesystem, DLL/provider state and caches | Windows/system resources reachable by process according to actual token, object security, Win32k/job and profile; preflight can mutate state that survives admission | Fresh profile and dynamic controls are configured today, but complete ambient input/output inventory is not established. Review access to existing OS state, shared resources, child-created handles and whether reset or mediation is possible; unknown routes prevent protected qualification. |
| WFP session and four filters | Broker owns dynamic session/IDs; worker receives no WFP-management authority | Existing strict test checks configured filters and later removes them for phase 2; prove target/layer/condition and checked cleanup for this actual worker, and separately observe the effect. Do not generalize diagnostic filters to the strict worker. |
| Console, desktop, clipboard, COM, networking, mappings, devices and inherited/duplicated handles | No unapproved effect or unmediated public output; any authorized result follows Bend's release path | Existing restrictions and tests are partial; USER32/OLE32/Winsock initialization failure is incomplete. A finite handle snapshot or mitigation bit does not rule out later creation or alternate paths. List each tested and unknown route. |
| Broker logs, errors, report values, timing, crash artifacts | Broker can expose observations outside worker; after protected input even small output fields may encode data | A fixed struct or numeric-only logging is not an information-flow proof. Specify the policy-allowed projection/rate, sink, authority and failure behavior, or prevent output; account for externally visible timing/crash state. |

The inventory is intentionally not labeled complete. `HostPrimitives.bend` treats `Inventory` as a **trusted binding's complete native route set**, but also states that the model cannot observe or authenticate it. An unverified list, worker self-report or preflight PSS snapshot must not be converted into that trusted fact. An inability to establish the required coverage remains an explicit native qualification gap.

## Proposed synthetic Bend model

This is a test-design sketch, not Bend source or a new law. Before any implementation, read the pinned Bend guides and the relevant OpenSpec baselines, and make a reviewed decision about where an adapter-local model belongs. Do not expose a new C policy engine or change existing security laws to make tests pass.

- **Authority baseline:** `HostIdentity.bend` binds monitor-allocated session identifiers, caller and incarnation; a wire reference is not a credential. `HostPrimitives.bend` stores configured worker profiles and has `admit_worker` resolve the nondelegable worker session/reference with a trusted monitor time, revision and trusted target/inventory facts. Its accepted `Step` emits `DeliverInputs`; a denied step has no effects. `HostPublication.bend` owns the separate publication gate. `writfs/Mount.bend` is a fixed public-canary model with its own `INIT`/`ADMIT`/`STAT`/`OPEN`/`READ`/`REVOKE` phases; it is not already an authenticated HostPrimitives session or a protected Windows host. Do not pretend those two paths are integrated.
- **Synthetic launch record:** a test-only monitor-owned binding represents a freshly allocated launch generation, expected retained process lifetime and image, selected configured profile and session/monitor incarnation. The adapter supplies authenticated launch/peer/control facts as assumptions; a worker message never supplies or chooses these facts. The existing HostPrimitives worker ID is allocated on admission, so a proposed preflight launch identifier is separate and must not be presented as an existing admitted worker ID or session credential.
- **Proposed preflight state:** define a closed finite sequence such as created → preflight report accepted → public handoff completed/retired → admission attempted → admitted/revoked/retired, with single-use phases, exact expected revision and generation, and no protected effect before the real admission decision. A report contains only bounded observation status and is not a grant; a handoff contains only public fixture parameters and cannot choose a capability, actor, profile or release decision. A denied transition returns unchanged security state and no effect. Timeout/cleanup failure may separately record a terminal failure without granting an effect; document which state changes are audit/lifecycle-only.
- **Composition boundary:** on the successful preflight path, invoke the existing monitor-owned authority/admission transition with its real configured profile, trusted complete inventory, session/reference and trusted time/revision; only an accepted `admit_worker` `DeliverInputs` is a protected-input effect. A synthetic stub can test phase sequencing but cannot be described as exercising the real HostPrimitives, Backplane commit, native identity or route checks. If a combined test calls those modules, assert their actual result/effects and preserve their original denial behavior. A check-then-deliver race needs an explicit atomic ordering or final revalidation; do not model a successful grant as permanently valid after revoke/restart.
- **Finite exhaustive scenarios:** test legal path and each missing/wrong report; stale revision, launch/session generation, image/profile or peer; duplicate/replayed/out-of-order messages; invalid/oversized/truncated/trailing data; caller-supplied actor/profile/capability; unmediated route; missing facts; timeout/crash/cleanup failure; `ADMIT`/handoff against revoke and monitor restart in both orders; changed capability/epoch/scope/budget/inherited restriction; and stale post-revoke completion. Assert no delivery/commit on pre-input failure, preserve already observed data on later revocation and deny subsequent use/stale release. Test meaningful transition results and actual effects, not just a mirror of the implementation. A finite set of enumerated interleavings is not a proof of all schedules.
- **Proof and traceability:** identify candidate safety laws and how they compose with existing identity, monitor, backplane and publication laws without weakening them. Give each test a named contract and explicit reviewed-only OS evidence gap. Use pinned Bend 2.0.39, `bend Tests.bend`, native tests and `bend PROOF.bend` for meaningful security changes; describe Lean `--verdict` and GPU limitations accurately. Model success cannot prove Windows object identity, DACLs, job enforcement, I/O cancellation or native confinement.

Before a protected implementation, the security review must select and fully specify the channel/effect policy, peer binding and race-safe transition. The native binding must continuously enforce the declared routes or fail incomplete; neither this model nor prior different-process diagnostics supplies that evidence.
