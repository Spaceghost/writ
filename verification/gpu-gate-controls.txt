Finding (observer): compute-sanitizer 2026.3.0.0 removes an empty CUDA_VISIBLE_DEVICES from its target's environment (the probe above: `set-empty` without the sanitizer, `unset` under it), while it passes a non-empty value through (`set:99`). In (c) and (d) the observed pass therefore ran on the device with 500 launches while the plain pass ran hidden. The gate refuses both pairs anyway (plain exit 1 and stdout differing in (d); mode in (c)), and observe.sh now probes what the sanitizer's target sees and records it as `target_cuda_visible_devices` beside `caller_cuda_visible_devices` in the observer field; check-record.sh fails any pair where they differ (`observer: target saw CUDA_VISIBLE_DEVICES 'unset', caller set 'set-empty' (environment not reproduced)`). Later tasks that hide the device should use an invalid id, not the empty string, when the observed pass must see the same environment.

Observed-pass exit status is compute-sanitizer's: 255 whenever the target makes no instrumented CUDA call ((b), and (c2), (d2), where cuInit fails before the sanitizer attaches), even when the probe itself exited 0 and printed PASS ((b), (c2)). The plain pass carries the probe's own exit status.

## Limits
- One probe (bang) and one binary. No Writ GPU path (Gpu.sweep, Dlm.batch, Transfer.batch) was run; those are Tasks 3 onward.
- A size argument (`--gpu 8GB`) was not run; the gate's mode rule accepts it by pattern only.
- The (a-long) pass shows the 10 s utilisation rule satisfied once; no long run was shown failing it. pmon remained sparse (4 of 18 rows numeric) on the shared GPU.
- (e) uses repeat 0 of the GPU-built bang; no separate probe without a GPU call was built (no new .bend file was in scope).
- The evidence files are unsigned run-local files. The gate catches records whose claims disagree with the evidence they name, missing evidence, truncated sanitizer output, a different target command line, and an environment the observer did not reproduce; it does not resist a forger who rewrites a log and its record consistently. binary_sha256 is hashed at run time and not re-hashed by check-record.sh, so a later rebuild does not invalidate an old record.
- device_name, device_uuid, device_bus and driver_version come from `nvidia-smi -i 0`, which ignores CUDA_VISIBLE_DEVICES; on this one-GPU host GPU 0 is the device cuDeviceGet(0) opens when it is visible. A multi-GPU host would need the mapping recorded.
- `cc` is the compiler the driver selects in this environment, not a fact read from the binary; the build is bound by emitted_c_sha256 and binary_sha256.
- lane_commit in every record is 23b82c8 with observe.sh and check-record.sh uncommitted; their sha256 in source_sha256 (efd08afb..., 7d4df17b...) equal the committed files.
- The host was loaded (1-minute load average up to 91.65) and the display shares the GPU; wall times are indicative only and are not performance results.
- gdb fallback, Nsight (absent), and device memory checking (all kernels excluded by design) not exercised. `bend Tests.bend` and `bend PROOF.bend` were not run: no .bend file or policy code changed.
