# Research: bounded no-data Windows handle snapshots and environment

Status: source research and feasibility design only. No PSS probe, native execution, remote environment read or change to the strict worker has been implemented or run. This is not evidence of complete inherited-handle or environment equivalence.

The [controlled-comparison design](controlled-comparison-design.md) requires more than the launcher's intended handle list and environment input. Microsoft documents a potential independent **point-in-time handle-table observation** through Process Snapshotting, but the exact behavior, access rights and resource usage for this target are not yet established. The documented environment APIs found here expose the calling process's environment, not an independent pre-resume read of another process. Until those limits are resolved, comparisons requiring full independent environment readback remain inconclusive.

## What the documented APIs actually offer

- [PssCaptureSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot) takes a target process handle and reports a Windows error code. The [PSS_CAPTURE_HANDLES flag](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags) says it captures the handle table's **values only**. This is a snapshot of that process at a point in time, not the identity, access rights, provenance or future state of every referenced object. Optional name, basic and type-specific flags are separate and are not needed in this feasibility slice; do not capture names, address spaces, memory, thread contexts, traces or clones.
- [PssQuerySnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-pssquerysnapshot) can return [PSS_HANDLE_INFORMATION.HandlesCaptured](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_handle_information). A [PssWalkSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psswalksnapshot) walk with `PSS_WALK_HANDLES` returns [PSS_HANDLE_ENTRY](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_handle_entry) values and normally ends at `ERROR_NO_MORE_ITEMS`. Compare the walk count with the reported snapshot count; equal counts are an internal consistency check, not proof that Windows omitted nothing. Reject truncation, duplicates, count discrepancies, API errors and unexpected end states.
- Retain the actual child process handle returned at creation. Compare its PID and creation FILETIME from [GetProcessId](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessid) and [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes), with a liveness check, before and after capture/walk; never reopen by PID alone. Where available, compare snapshot process metadata to that same lifetime. These checks bind the observation to a retained native process lifetime, not a human identity or Writ actor. The initial child thread is held suspended and no test child is admitted to data. A snapshot is still only instantaneous, and external system actors or later process activity can change the table.
- As a cross-check, [GetProcessHandleCount](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesshandlecount) reports a count using `PROCESS_QUERY_INFORMATION` or `PROCESS_QUERY_LIMITED_INFORMATION`; it cannot identify handles. Query it immediately before and after the snapshot, retain all three counts and treat unexplained disagreement as inconclusive. These are separate observations, not an atomic guarantee.
- The [explicit inherited handle list](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) is a trusted launcher input. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) describes inherited handles as having the same value and access rights as the source. Finding a value in the snapshot is useful, but by itself does not prove an object's type or provenance or show that other entries were inherited rather than created by Windows. Do not blindly assume that every table entry must be the one pipe.
- The Microsoft PSS capture reference does **not** specify the minimum target-process rights for `PSS_CAPTURE_HANDLES`; do not claim a particular minimum or add blanket privileges. The feasibility code must use only its retained self-created child handle, record the rights actually supplied by its launch design, and treat access denied/unsupported as an unverified result. A separately considered object-identity check may duplicate only a known synthetic child handle into the observer with [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle), which requires `PROCESS_DUP_HANDLE` on the source process, then compare it with a retained owner handle using [CompareObjectHandles](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-compareobjecthandles). Never use `DUPLICATE_CLOSE_SOURCE`. This broader inspection capability is confined to the self-created, no-data child and is not a portable credential. It must be separately reviewed for side effects; a failure or unsupported object comparison is unknown, not evidence that an object is absent. [Microsoft warns](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights) that `PROCESS_DUP_HANDLE` can enable broader access; do not apply this to a real byte worker.
- A walk marker is freed with [PssWalkMarkerFree](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psswalkmarkerfree); [PssFreeSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-pssfreesnapshot) specifies `GetCurrentProcess()` for a snapshot captured in the local process. Both return statuses must be checked. Its documented remote-snapshot free rights do not establish the rights required to capture a target's handles locally. The documentation does not give a per-call time or internal memory bound for PSS capture, so a bounded walk alone does not prove the whole operation is bounded.

## Proposed small feasibility test

On a fresh disposable Windows VM, with no Writ policy, mount, fixture bytes, data worker, arbitrary PID argument or other cross-process target, an independently reviewed fixed observer accepts no caller-selected child image, command line, fixture or handle and creates and retains one suspended synthetic child from its own fixed executable plus a supervisor-created private pipe/event fixture. The child is designed to perform no data reads or network operations. The observer may query or duplicate handles **only from that child**. It may create multiple sequential children for positive/negative controls, but never inspect an unrelated process. A dedicated, unprivileged environment, one child at a time, a parent job/process memory and time budget, fixed-size output, and an external CI deadline constrain the test; if PSS or cleanup hangs, the result is incomplete and disposable-VM destruction is fallback, not verified cleanup. Nested-job compatibility and any PSS internal resource limits remain untested.

1. Create a suspended no-data child with a fixed explicit inherited list containing known owned synthetic handles, e.g. the report-pipe endpoint and one event; keep the parent's matching handles open. Record only local test identifiers, PID, creation time, and expected numeric handle values, never arbitrary object names or user data. Verify `GetProcessId`, `GetProcessTimes`, process liveness, child-thread suspension established by creation path, job limits, and exact launch flags before capture. Do not claim that a launch attribute is an independent readback.
2. Request only `PSS_CAPTURE_HANDLES` on the retained child handle. Query `HandlesCaptured` and cap accepted counts at a proposed **256**. Create a walk marker, read at most 256 fixed-size `PSS_HANDLE_ENTRY` records plus one terminal call, accept only a documented `ERROR_NO_MORE_ITEMS` after all entries, require the number read to equal the reported count, reject duplicate/invalid values, and compare `GetProcessHandleCount` before and after. Any failure, unknown discrepancy, size overflow or inability to obtain the handle snapshot is **incomplete**. Record only bounded aggregate results and statuses; do not log names, pointers or memory. The cap is a proposed fixture limit, not a Windows limit.
3. Positive controls require the known inherited pipe and event values to occur in the captured set, while checking the matching parent-side objects are still alive. A separately reviewed control may duplicate those two exact synthetic child handles into the observer and use `CompareObjectHandles` against the held originals, then close the duplicates and record errors. `PROCESS_DUP_HANDLE` and object comparison limitations are as stated above. A separate negative launch deliberately leaves a known inheritable synthetic handle outside the explicit list; the observation is useful only if that expected numeric handle value is absent alongside valid positive controls and a complete walk; it does not prove the underlying object could not appear under a different handle. Also inject synthetic parser cases for a missing expected value, one extra value, duplicate entries, count mismatch, too many entries, early termination, API failure and cleanup failure. Extra table entries must be accounted for or the exact-set question remains unknown; the tests must not assume their source.
4. Keep the child suspended while performing this point-in-time snapshot. Free the walk marker and local snapshot, checking each return code; close all supervisor-held duplicates and fixture handles, retire the child/job and verify process exit and handle closure. Never continue to another control after failed cleanup. A failed capture or erased cleanup state remains incomplete, and the disposable runner's destruction is merely fallback containment. Record source/binary hashes, platform version, actual error codes, bounded counts and explicit cleanup outcomes.

This can answer whether this OS/build and fixed fixture expose the expected synthetic handle values under one captured lifetime. It does not by itself distinguish inherited from OS-created entries, establish inherited object authority or prove that an LPAC worker, another process or later lifetime has the same table. LPAC-specific compatibility, held process rights, stable snapshot completeness, identity of a pipe object and any ability to capture without perturbing the actual diagnostic must be separately verified before use in comparisons.

## Environment remains a separate gap

[GetEnvironmentStringsW](https://learn.microsoft.com/en-us/windows/win32/api/processenv/nf-processenv-getenvironmentstrings) explicitly returns the calling process's environment; [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) accepts a supplied environment block, and Microsoft describes the double-NUL-terminated [environment format](https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables). The input block is a trusted construction fact, not independent proof of the suspended child's full block. A carefully bounded child self-report after resume can provide a distinct observation, but it cannot prove the pre-resume state or authenticate itself as an independent OS readback.

Microsoft marks [NtQueryInformationProcess](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess), [PEB](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-peb) and [RTL_USER_PROCESS_PARAMETERS](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-rtl_user_process_parameters) as subject to change; the published process-parameters structure does not expose a supported environment member. Reading private PEB offsets or scanning another process's memory is therefore not established here as a supported, stable full-environment solution. Do not use it as proof, infer that no environment exists, or weaken the comparison requirement. Research may continue, but no independent complete before-resume environment method has been established.
