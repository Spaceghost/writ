Where should the first Linux bridge get its authority?

Josh, we can continue building the authenticated session and live-authority bridge. For its first real Linux profile, should we design around a locally operated authority, or is there an existing identity or authority service you want it to use?

Why this matters

The current Linux canary runs a real native process but uses synthetic authority. The Bend issuance model can rebuild current grants, revocations and registry projections; no Linux host currently authenticates that model's submissions or supplies its current state and trusted time. A Linux UID, PID or pidfd can help identify a local process but does not by itself establish the original person's identity or permission to disclose data.

A first local profile could have a trusted local operator or supervisor authenticate the reader, administer the issuer state and provide a monotone clock. Source and destination authority and their separate obligations would still be checked in Bend. The design would need to specify bootstrapping, ownership, revocation, restart and recovery, and protect the channel carrying those facts. This is a proposed development profile, not an existing implementation or production qualification.

An existing service could instead be the trust root, but we need to know which service and how it represents the reader and the two sides' authority before designing that binding. We can continue independent model and native cleanup work while you decide.
